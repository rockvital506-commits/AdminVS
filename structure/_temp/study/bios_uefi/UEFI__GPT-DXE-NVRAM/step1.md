[🎓 Подробный разбор: что такое GPT и ESP (для начинающего)]

### 🔸 Простая аналогия
> Представь диск как книгу:
> - **MBR** — оглавление на первой странице (одно, легко порвать)
> - **GPT** — два оглавления (в начале и в конце) + номера страниц в 64-битном формате + контрольные суммы [[1]][[7]]
> - **ESP** — специальная закладка в начале книги, где лежит инструкция "как открыть книгу" (bootloader), написанная на универсальном языке (FAT32), который понимает любой читатель (UEFI) [[15]][[91]]

### 🔸 GPT: 5 вещей, которые нужно запомнить
1. **Protective MBR (LBA 0)** — "щит" от старых программ, которые не знают про GPT. Не трогай его вручную [[9]].
2. **Два заголовка** — Primary (LBA 1) и Backup (LastLBA). Если один повредится, второй восстановит [[38]].
3. **Массив записей (128 шт.)** — каждая описывает раздел: где начинается, где кончается, какой тип. Тип = GUID, не число [[91]].
4. **ESP — особый раздел** — ищи по GUID `C12A7328...`, форматируй только в FAT32, размер ≥300 МБ для современных дисков [[15]].
5. **CRC32** — "цифровая подпись" заголовка и массива. Если не совпадает → утилита предложит восстановить из бэкапа [[45]].



### 🔸 Почему FAT32? Почему не NTFS?
- UEFI-прошивка содержит минимальный FAT-драйвер (простой, надежный) [[91]]
- Поддержка FAT32 есть в любой прошивке, даже если ОС ещё не загрузилась
- Ограничение: файлы ≤4 ГБ — но загрузчики весят <10 МБ, так что не проблема

### 🔹 Ситуация 1: «ESP не монтируется / буква не назначается»
**Симптомы**: `diskpart` не видит раздел "System", или `assign letter=Z` выдает ошибку "Неверная функция".
**Причина**: Раздел скрыт, имеет атрибут `HIDDEN`, или драйвер файловой системы не загрузился.

| Этап | Действия |
|------|----------|
| **🎯 Алгоритм выбора инструмента** | 1. `diskpart` (базовый доступ) → 2. `mountvol` (альтернативный маунт) → 3. `RWEverything` (только чтение атрибутов, если предыдущие не сработали). |
| **⚙️ Рекомендуемые действия** | 1. `diskpart` → `list disk` → `sel disk 0` → `list part`. Ищи раздел 100-300 МБ с типом **System**.<br>2. Если не виден: `detail disk` → проверь, есть ли раздел без буквы.<br>3. Альтернатива: `mountvol Z: /S` (принудительный маунт ESP на Z:).<br>4. Проверка ФС: `fsutil fsinfo volumeinfo Z:` (должно быть FAT32). |
| **✅ Ожидаемый результат** | Буква `Z:` назначена, `dir Z:\EFI\Microsoft\Boot` показывает файлы. |
| **❌ Неожиданный результат** | Ошибка "The parameter is incorrect" или доступ запрещен.<br>→ **Действия**: 1) Перезагрузка в WinPE (через Ventoy); 2) Проверка `attributes volume` в diskpart (снять `Hidden` командой `attributes volume clear Hidden`); 3) Если диск динамический — вернуть к базовому (потеря данных!). |

### 🔹 Ситуация 2: «Пропадает загрузочная запись после обновления Windows»
**Симптомы**: После `Windows Update` ноутбук грузится сразу в Windows, игнорируя Ventoy/GRUB/Linux.
**Причина**: Обновление переустанавливает `bootmgfw.efi` и перезаписывает переменную NVRAM `BootOrder`, ставя Windows на 1-е место.

| Этап | Действия |
|------|----------|
| **🎯 Алгоритм выбора инструмента** | 1. `bcdedit /enum firmware` (просмотр) → 2. `efibootmgr` (из Linux/WSL2) или `bcdedit /set {bootmgr} path` (из Windows) → 3. UEFI Setup (BIOS) для сброса приоритета. |
| **⚙️ Рекомендуемые действия** | 1. Загрузись в основную Windows.<br>2. Запусти `bcdedit /enum firmware` — найди идентификатор `{xxxx}` для нужного загрузчика.<br>3. Если нужно восстановить путь: `bcdedit /set {bootmgr} path \EFI\Microsoft\Boot\bootmgfw.efi`.<br>4. Для дуал-бута: используй `efibootmgr -o XXXX,YYYY` (где XXXX — нужный загрузчик). |
| **✅ Ожидаемый результат** | При перезагрузке появляется меню выбора ОС или грузится нужный загрузчик. |
| **❌ Неожиданный результат** | `bcdedit` пишет "Access denied" или изменения не сохраняются.<br>→ **Действия**: 1) Отключи **Secure Boot** временно; 2) Проверь, не включен ли **Fast Startup** (выключи в `powercfg /h off`); 3) Сбрось NVRAM через `SetupUtility → Save & Exit → Restore Defaults` (осторожно: сбросит и другие настройки). |

### 🔹 Ситуация 3: «Конфликт загрузчиков в ESP при дуал-буте»
**Симптомы**: После установки Linux перестала грузиться Windows (или наоборот), или в меню загрузки "мусор" из старых записей.
**Причина**: Несколько загрузчиков в одной папке `\EFI\Boot\`, или перезапись `bootx64.efi` (fallback-имя).

| Этап | Действия |
|------|----------|
| **🎯 Алгоритм выбора инструмента** | 1. `tree /F Z:\EFI` (визуализация структуры) → 2. `efibootmgr -v` (анализ записей) → 3. Ручное переименование/перемещение файлов в проводнике (только после бэкапа!). |
| **⚙️ Рекомендуемые действия** | 1. Сделай бэкап всей папки `Z:\EFI` в `Z:\EFI_Backup`.<br>2. Проверь структуру: у каждой ОС должна быть своя папка (`\EFI\Microsoft`, `\EFI\ubuntu`, `\EFI\BOOT`).<br>3. Файл `\EFI\BOOT\BOOTX64.EFI` — это fallback, он не должен быть основным для конкретной ОС.<br>4. Удали "битые" записи: `efibootmgr -b XXXX -B` (где XXXX — номер записи). |
| **✅ Ожидаемый результат** | Чистая структура, каждый загрузчик в своей папке, NVRAM содержит только актуальные записи. |
| **❌ Неожиданный результат** | После удаления записи система не грузится вообще.<br>→ **Действия**: 1) Восстанови папку `EFI` из бэкапа; 2) Загрузись с установочной флешки → `Repair → Startup Repair`; 3) Используй `bootrec /rebuildbcd` (только для Windows). |

### 🔹 Ситуация 4: «GPT corruption: CRC mismatch / Backup header used»
**Симптомы**: `chkdsk` или `gdisk` ругаются: "GPT headers do not match", "Primary header corrupted, using backup".
**Причина**: Сбой питания, битые сектора в области LBA 1-33, ошибка записи.

| Этап | Действия |
|------|----------|
| **🎯 Алгоритм выбора инструмента** | 1. `gdisk` (Linux/WinPE) — режим восстановления → 2. `TestDisk` — авто-поиск структур → 3. `chkdsk /f` — только для проверки ФС (не структуры!). |
| **⚙️ Рекомендуемые действия** | 1. **Не записывай ничего на диск** до анализа.<br>2. Запусти `gdisk /dev/nvme0n1` → нажми `v` (verify).<br>3. Если `gdisk` предлагает восстановить из backup: нажми `b` (use backup) → затем `w` (write) **только если уверен**.<br>4. Альтернатива: `TestDisk` → `Analyse` → `Quick Search` → покажет, видит ли он разделы. |
| **✅ Ожидаемый результат** | `gdisk` сообщает "No problems found" после восстановления, разделы видны в Windows. |
| **❌ Неожиданный результат** | После записи диск стал "RAW" или пропали разделы.<br>→ **Действия**: 1) **Немедленно остановись**; 2) Создай посекторный образ (`ddrescue`/`HDDRawCopy`); 3) Восстанавливай данные с образа через `R-Studio`/`DMDE`, а не с физического диска. |

### 🔹 Ситуация 5: «Ventoy не видит загрузочные образы / черный экран»
**Симптомы**: Меню Ventoy появляется, но при выборе ISO — черный экран или возврат в меню.
**Причина**: Образ требует Secure Boot, но ключи не подписаны; или образ использует legacy-загрузку, а в BIOS включен UEFI-only.

| Этап | Действия |
|------|----------|
| **🎯 Алгоритм выбора инструмента** | 1. Проверка режима BIOS (`msinfo32` → BIOS Mode) → 2. Настройка `ventoy.json` (параметры загрузки) → 3. Обновление Ventoy на флешке. |
| **⚙️ Рекомендуемые действия** | 1. В BIOS: проверь, что **Secure Boot = Disabled** (для тестов) или обнови ключи Ventoy (`enroll_hash`).<br>2. Для специфичных образов: создай `ventoy.json` на флешке:<br>`{"image_list": [{"image":"/iso/custom.iso", "boot_mode":"normal"}]}`.<br>3. Обновись: запусти `Ventoy2Disk.exe` → `Update` (данные на флешке сохранятся). |
| **✅ Ожидаемый результат** | Образ грузится корректно, попадает в меню загрузчика внутри ISO. |
| **❌ Неожиданный результат** | Ошибка "Invalid signature" или "Boot failed".<br>→ **Действия**: 1) Попробуй загрузить этот ISO напрямую (без Ventoy) через `Write in ISO mode`; 2) Проверь целостность ISO (SHA256); 3) Если образ старый — включи **CSM** (Legacy) в BIOS, но помни: это может сломать загрузку основной Win11. |

### 🔹 Ситуация 6: «Случайное удаление файлов из ESP»
**Симптомы**: После "чистки диска" или ручного удаления файлов ноутбук выдает "No bootable device".
**Причина**: Удален `bootmgfw.efi`, `BCD` или драйверы загрузки.

| Этап | Действия |
|------|----------|
| **🎯 Алгоритм выбора инструмента** | 1. `Recuva`/`PhotoRec` (попытка восстановления файлов) → 2. `bcdboot` (пересоздание загрузчика) → 3. Установка с нуля (крайний случай). |
| **⚙️ Рекомендуемые действия** | 1. **Не форматируй ESP** и не создавай новые разделы.<br>2. Загрузись с установочной флешки Win11 → `Shift+F10`.<br>3. Смонтируй заново: `diskpart` → `assign letter=Z` для ESP, `assign letter=C` для Windows.<br>4. Пересоздай загрузчик: `bcdboot C:\Windows /s Z: /f UEFI`.<br>5. Проверь: `dir Z:\EFI\Microsoft\Boot`. |
| **✅ Ожидаемый результат** | Появляются файлы `bootmgfw.efi`, `BCD`, система грузится. |
| **❌ Неожиданный результат** | `bcdboot` выдает "Failure when copying files".<br>→ **Действия**: 1) Проверь, не бит ли образ `install.wim` на флешке; 2) Попробуй `bootrec /fixboot` (может потребовать `bootsect /nt60 sys /force`); 3) Если ESP поврежден ФС: `format Z: /FS:FAT32 /Q /V:ESP` (только если есть бэкап данных или готов к переустановке!). |

### 🔹 Ситуация 7: «Инициализация диска: выбор MBR/GPT»
**Симптомы**: При подключении нового диска/ССД в `diskmgmt.msc` предлагается "Инициализировать диск".
**Причина**: Диск новый или таблица разделов повреждена/удалена.

| Этап | Действия |
|------|----------|
| **🎯 Алгоритм выбора инструмента** | 1. `msinfo32` (проверка режима загрузки текущей ОС) → 2. `diskpart` (ручная инициализация с контролем) → 3. `Convert` (если нужно сменить тип без потери данных — но это рискованно). |
| **⚙️ Рекомендуемые действия** | 1. Если система грузится в **UEFI** → выбирай **GPT** (обязательно для дисков >2 ТБ и загрузки Win11).<br>2. Если диск **дополнительный** (не загрузочный) → всё равно выбирай GPT для совместимости с современными ОС.<br>3. Команда: `diskpart` → `select disk X` → `clean` → `convert gpt`. |
| **✅ Ожидаемый результат** | Диск инициализирован, виден как "Не распределен", готов к созданию разделов. |
| **❌ Неожиданный результат** | После инициализации диск не виден или просит форматировать.<br>→ **Действия**: 1) Проверь в `diskpart` → `detail disk` → не стоит ли атрибут `Read-only` (снять: `attributes disk clear readonly`); 2) Если диск внешний — проверь кабель/порт (недостаток питания может давать ложные ошибки инициализации). |

### 🔹 Ситуация 8: «Secure Boot блокирует кастомный загрузчик»
**Симптомы**: При попытке загрузить свой `.efi` (например, самописный или от неподписанного проекта) — ошибка "Security violation" или "Invalid signature".
**Причина**: Secure Boot проверяет цифровую подпись `.efi` против ключей в базе `db`; твоего ключа там нет.

| Этап | Действия |
|------|----------|
| **🎯 Алгоритм выбора инструмента** | 1. `mokutil --sb-state` (проверка статуса) → 2. Подпись своим ключом (`sbsign`) или отключение Secure Boot → 3. Enrollment ключа в MOK (Machine Owner Key). |
| **⚙️ Рекомендуемые действия** | **Вариант А (безопасный для новичка)**: В BIOS → `Secure Boot = Disabled` → сохрани → перезагрузка. Работает, но снижает безопасность.<br>**Вариант Б (правильный)**: 1) Сгенерируй пару ключей (`openssl`); 2) Подпиши `.efi`: `sbsign --key my.key --cert my.crt bootx64.efi`; 3) В BIOS → `Enroll Key` → загрузи `my.crt` в базу `db` или `MOK`. |
| **✅ Ожидаемый результат** | Загрузчик выполняется, система стартует. |
| **❌ Неожиданный результат** | После подписи всё равно ошибка, или система не видит ключ.<br>→ **Действия**: 1) Проверь, что подпись наложена на правильный файл (не на копию); 2) Убедись, что хеш-сумма сертификата совпадает с загруженным в MOK; 3) Временно отключи Secure Boot для отладки, но помни: это "костыль", а не решение. |

### 🔹 Ситуация 9: «4K-секторный диск: ESP не создается/не виден»
**Симптомы**: При создании ESP через `diskpart` на новом NVMe раздел "съезжает", или загрузка падает с ошибкой.
**Причина**: Физический размер сектора 4096 байт, а утилита выравнивает по 512 байт; или размер ESP < 300 МБ (не влезает минимальный набор файлов с учетом кластеров).

| Этап | Действия |
|------|----------|
| **🎯 Алгоритм выбора инструмента** | 1. `fsutil fsinfo sectorinfo C:` (проверка размера сектора) → 2. `diskpart` с явным указанием `align=1024` → 3. Выделение под ESP ≥ 300 МБ. |
| **⚙️ Рекомендуемые действия** | 1. При создании: `create partition efi size=300 align=1024` (выравнивание по 1 МБ).<br>2. Форматирование: `format quick fs=fat32 label="System"`.<br>3. Проверка: `fsutil fsinfo fatinfo Z:` → `BytesPerSector` должен быть 512 (логический), но `Clusters` должны быть выровнены. |
| **✅ Ожидаемый результат** | Раздел создан, смонтирован, файлы копируются без ошибок. |
| **❌ Неожиданный результат** | Ошибка "The media is write protected" или "Parameter is incorrect".<br>→ **Действия**: 1) Проверь, не включен ли **BitLocker** на диске (сними временно); 2) Убедись, что используешь `diskpart`, а не графический менеджер (он может не учитывать align); 3) Если диск с завода имеет 4K — пересоздай таблицу разделов с нуля (`clean` + `convert gpt`). |

### 🔹 Ситуация 10: «Восстановление из Backup GPT после сбоя»
**Симптомы**: Система не грузится, `diskpart` показывает "GPT Protective" или разделы пропали, но `gdisk` предлагает восстановить.
**Причина**: Поврежден Primary GPT (LBA 1-33), но Backup (на конце диска) цел.

| Этап | Действия |
|------|----------|
| **🎯 Алгоритм выбора инструмента** | 1. `gdisk` (режим recovery) → 2. `TestDisk` (авто-восстановление) → 3. Ручное копирование хедера (только для экспертов!). |
| **⚙️ Рекомендуемые действия** | 1. Загрузись с LiveUSB (Linux/WinPE).<br>2. `gdisk /dev/nvme0n1` → нажми `v` (verify).<br>3. Если пишет "Main header corrupt, using backup": нажми `b` (use backup for primary).<br>4. **Важно**: сначала нажми `p` (print) и сверь, что разделы выглядят логично.<br>5. Только потом `w` (write) → подтверди `Yes`. |
| **✅ Ожидаемый результат** | Таблица разделов восстановлена, диск виден в ОС, данные на месте. |
| **❌ Неожиданный результат** | После записи разделы "поехали" или стали нечитаемыми.<br>→ **Действия**: 1) **Не паникуй** — данные, скорее всего, целы, просто таблица сбилась; 2) Не записывай ничего нового; 3) Используй `TestDisk` → `Undelete` для восстановления файлов; 4) Если критично — неси в сервис для посекторного восстановления (не делай `chkdsk /f` на поврежденной структуре!). |

---

[🛡️ Общие правила безопасности для всех сценариев]
1. **Бэкап перед записью**: Всегда делай `dd if=/dev/nvme0n1 of=backup_header.img bs=512 count=68` (для GPT) или копируй папку `EFI` перед изменениями.
2. **Изоляция**: Тестируй деструктивные команды (`clean`, `format`, `write`) сначала на виртуальной машине или на втором диске.
3. **Чтение > Запись**: Сначала `list`, `print`, `enum` — убедись, что выбрал правильный диск/раздел, только потом `select` + действие.
4. **Логирование**: Сохраняй вывод команд в файл: `diskpart > log.txt` — если что-то пойдет не так, будет что анализировать.
5. **Точка возврата**: Имей под рукой загрузочную флешку с `cmd` (WinPE) — это твой "спасательный круг", если система перестанет грузиться.

[RECOMMEND]
1. Создай папку `C:\Recovery\GPT_ESP` и положи туда: 1) эту шпаргалку, 2) скрипт `backup_esp.bat` (`robocopy Z:\ C:\Recovery\ESP_Backup /E`), 3) ссылку на официальный образ WinPE.
2. Потренируй Ситуацию №1 и №6 на виртуальной машине (Hyper-V/WSL2 с подключенным виртуальным диском) — это самые частые кейсы.

[ANTICIPATE]
- "Как быстро проверить, живой ли ESP, не монтируя его?" → `diskpart → list part` → если раздел "System" есть и размер ~100-300 МБ, скорее всего, жив. Для глубже: `fsutil fsinfo fatinfo` (требует маунта).
- "Можно ли автоматизировать бэкап ESP?" → Да, задача `schtasks` + скрипт `robocopy` раз в неделю. Но помни: бэкап файлов ≠ бэкап NVRAM-переменных (для них нужен `efivar`/`RW`).
