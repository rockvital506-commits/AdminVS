### 📦 Ядро: где и как хранятся переменные
| Компонент | Расположение | Доступ | Ключевые переменные |
|-----------|--------------|--------|---------------------|
| **SPI NOR Flash** (16-64 МБ) | Регион `NVRAM` (обычно 256-512 КБ) [[1]][[87]] | Прямой (RWEverything) + API (GetVariable) | Все `NV`-переменные: `BootOrder`, `PK`, `KEK`, `db`, `dbx` |
| **RAM (volatile)** | Выделяется DXE Core при старте | Только API, до `ExitBootServices()` | `BootService`-переменные без `NV`-атрибута |
| **TPM 2.0 NV** | Отдельный регион внутри TPM [[55]] | Через TCG-протоколы | `PCR`-хеши, `authPolicy` для ключей |
| **Registry Mirror (Windows)** | `HKLM\SYSTEM\CurrentControlSet\Control\SecureBoot` [[69]] | Только чтение ОС | Кэшированные значения для драйверов |

**Физическая структура NVRAM в SPI** [[2]][[86]]:
```
[SPI Flash Layout]
├─ 0x000000-0x0FFFFF: Firmware Code (DXE, PEI, SEC)
├─ 0x100000-0x13FFFF: NVRAM Primary (переменные, заголовки, данные)
├─ 0x140000-0x17FFFF: NVRAM Backup (зеркало для восстановления)
├─ 0x180000-0x1FFFFF: Vendor Data / ME Region / Unused
```
- Каждая переменная = `Header (Name+GUID+Attrs+Size) + Data + CRC32`
- Wear-leveling: firmware чередует запись между Primary/Backup для продления жизни флеша (10-100К циклов) [[84]][[91]]
- Атомарность: запись переменной = "сначала в Backup, потом в Primary" — при сбое питания остаётся валидная копия

### 🔑 Ключевые переменные (где искать)
| Переменная | Имя | GUID | Атрибуты | Где используется |
|------------|-----|------|----------|-----------------|
| **BootOrder** | `BootOrder` | `EFI_GLOBAL_VARIABLE` | NV, BS, RT | Определяет очередь загрузки: `0001,0002,0003` → `Boot0001`, `Boot0002`... [[54]] |
| **Boot####** | `Boot0001`, `Boot0002`... | `EFI_GLOBAL_VARIABLE` | NV, BS, RT | Содержит `EFI_LOAD_OPTION`: путь к `.efi`, аргументы, FriendlyName |
| **Timeout** | `Timeout` | `EFI_GLOBAL_VARIABLE` | NV, BS, RT | Таймаут меню загрузки в секундах (0 = мгновенный старт) |
| **SecureBoot** | `SecureBoot` | `EFI_GLOBAL_VARIABLE` | BS, RT | Флаг: 1=включён, 0=выключен (read-only после загрузки) |
| **PK/KEK/db/dbx** | `PK`, `KEK`, `db`, `dbx` | `EFI_GLOBAL_VARIABLE` / `EFI_IMAGE_SECURITY_DATABASE_GUID` | NV, BS, RT, **AT** | Ключи цепочки доверия; `AT` = Time-based Authenticated Write [[10]][[12]] |
| **SetupMode** | `SetupMode` | `EFI_GLOBAL_VARIABLE` | BS, RT | 1=режим настройки (можно менять ключи), 0=развёрнутый режим |

### 🧭 2 Дополнительных направления (проведены)

**1. Аутентифицированные переменные (Authenticated Variables)**
- *Что*: Переменные с атрибутами `TIME_BASED_AUTHENTICATED_WRITE_ACCESS` или `ENHANCED_AUTHENTICATED_ACCESS` требуют цифровой подписи при изменении [[48]][[50]].
- *Зачем*: Защита `PK/KEK/db/dbx` от несанкционированной модификации.
- *Как работает*: При `SetVariable()` передаётся структура `EFI_VARIABLE_AUTHENTICATION_2` (TimeStamp + PKCS#7 подпись) [[28]]. Прошивка проверяет подпись против текущего ключа перед записью.
- *Практика*: Для обновления `dbx` (черный список) нужно: 1) иметь приватный ключ, соответствующий `KEK`; 2) подписать новую запись; 3) вызвать `SetVariable()` с дескриптором. Без подписи → `EFI_SECURITY_VIOLATION`.

**2. Восстановление при коррупции NVRAM**
- *Проблема*: Сбой питания во время записи → CRC mismatch → переменные недоступны [[39]][[41]].
- *Механизм восстановления*: 
  1. Firmware при старте проверяет CRC Primary/Backup NVRAM.
  2. Если Primary повреждён → копирует Backup в Primary.
  3. Если оба повреждены → сбрасывает к дефолтным значениям (`*Default` переменные) [[44]].
- *Инструменты*: 
  - `chipsec` (`chipsec_util uefi var-list`) — чтение без записи.
  - `RWEverything` — прямой доступ к регионам (только чтение!).
  - `efivar` (Linux) — экспорт/импорт переменных.
- *Риск*: Прямая запись через `RW` без понимания структуры → необратимый кирпич.

[MAIN] 📖 Подробный разбор: что такое NVRAM и UEFI-переменные

### 🔹 Простая аналогия
> Представь NVRAM как **сейф с ячейками**:
> - **Ячейка** = переменная (имя + содержимое).
> - **Метка на ячейке** = атрибуты (`NV` = не стирается при выключении, `RT` = доступна ОС).
> - **Ключ от ячейки** = `VendorGuid` (чтобы не перепутать переменные разных вендоров).
> - **Охрана** = аутентификация (для ключей Secure Boot нужен "отпечаток" — подпись).
> - **Дубликат ключа** = Backup-регион (если основной сейф повредится, есть копия).

### 🔹 5 правил, которые нужно запомнить
1. **Атрибуты решают всё** [[28]][[49]]:
   - `NV` (Non-Volatile) → сохраняется после выключения.
   - `BS` (Boot Services) → видна только до `ExitBootServices()`.
   - `RT` (Runtime) → видна и в ОС.
   - `AT` (Authenticated) → требует подписи при записи.
   - Пример: `Timeout` имеет `NV,BS,RT` → можно менять из Windows, сохранится после перезагрузки.

2. **Глобальные переменные используют один GUID** [[54]]:
   - Все `Boot####`, `BootOrder`, `Timeout` используют `EFI_GLOBAL_VARIABLE` (`{8BE4DF61-93CA-11d2-00E0-9803-2B8C}`).
   - Это значит: `GetVariable("BootOrder", EFI_GLOBAL_VARIABLE, ...)` вернёт очередь загрузки.

3. **Secure Boot-ключи — особый случай** [[10]][[12]]:
   - `PK` (Platform Key) → корень доверия.
   - `KEK` (Key Exchange Key) → подписывает обновления `db`.
   - `db` (Authorized Signatures) → белые списки.
   - `dbx` (Forbidden Signatures) → чёрные списки.
   - Все имеют атрибут `AT` → нельзя изменить без подписи соответствующим ключом.

4. **Запись = атомарная операция** [[91]]:
   - Firmware сначала пишет в Backup-регион, проверяет CRC, потом копирует в Primary.
   - При сбое питания остаётся хотя бы одна валидная копия.
   - Поэтому `SetVariable()` может занимать десятки миллисекунд — не вызывай его в цикле!

5. **ОС видит не всё** [[9]][[72]]:
   - После `ExitBootServices()` переменные без `RT` исчезают.
   - Windows кэширует некоторые значения в реестре (`HKLM\...\SecureBoot`), но это копия, а не источник истины.
   - Для полной картины используй `efivar` (Linux) или `GetFirmwareEnvironmentVariable` (Windows API).

### 🔹 Как читать/писать безопасно (твой сценарий)
```powershell
# Windows: прочитать BootOrder (PowerShell от администратора)
$guid = [Guid]::Parse("8BE4DF61-93CA-11d2-00E0-9803-2B8C") # EFI_GLOBAL_VARIABLE
$bytes = [byte[]]::new(1024)
$size = [uint32]1024
$attrs = [uint32]0
$result = [Microsoft.Win32.UnsafeNativeMethods]::GetFirmwareEnvironmentVariable("BootOrder", $guid, $bytes, [ref]$size)
# $bytes[0..$size-1] содержит массив UINT16 (номера загрузок: 0001, 0002...)

# Linux: то же через efivar (безопасно, только чтение)
efivar -l | grep BootOrder          # найти переменную
efivar -d -n BootOrder-8be4df61-93ca-11d2-00e0-98032b8c  # вывести данные

# Важно: никогда не пиши в PK/KEK/db/dbx без подписи!
# Для тестов используй переменные без AT-атрибута, например "TestVar" с уникальным GUID.
```

### 🔹 Почему аутентификация критична для безопасности
- Без `AT` любой процесс с правами администратора мог бы заменить `dbx` и отключить Secure Boot.
- С `AT`: даже админ не может изменить ключи без приватного ключа вендора.
- Это защищает от атак типа "Bootkit" — вредонос не может подменить загрузчик, если его подпись не в `db`.

[IF SOFT] 🎓 Ментор: пояснения для beginner
- `NV ≠ CMOS`: NVRAM хранится в SPI-флеше, а не в батарейке. Сброс NVRAM ≠ снятие батарейки.
- `GetVariable` vs `SetVariable`: Чтение безопасно почти всегда. Запись — только если понимаешь атрибуты и имеешь права.
- `BootOrder` — это не список файлов, а список "ссылок" на `Boot####`-переменные. Сначала читаешь `BootOrder`, потом для каждого ID читаешь `Boot####` чтобы узнать путь к `.efi`.
- `Timeout=0` — опасная настройка: меню загрузки не покажется, система стартует сразу в первую запись. Если `Boot0001` битый → черный экран. Всегда имей запасной вариант.
- `Масштабирование`: После освоения базовых переменных перейди к `chipsec` (`chipsec_util uefi var-list`) для аудита и `edk2` для понимания, как переменные создаются в прошивке.

### 🔹 Ситуация 1: «Пустой BootOrder после сброса/обновления»
**Симптомы**: `efibootmgr` или `bcdedit /enum firmware` показывает пустой `BootOrder`, но `Boot####`-переменные существуют. Ноутбук не грузится или загружает дефолтный загрузчик.
**Причина**: Сбой записи, обновление BIOS, коррупция первичного региона NVRAM.

| Этап | Действия |
|------|----------|
| **🎯 Алгоритм выбора инструмента** | 1. `efibootmgr -v` (Linux/WSL2) или `bcdedit /enum firmware` (Win) → 2. `efivar -l` (полный список) → 3. `RWEverything` (только чтение, для эксперта). |
| **⚙️ Рекомендуемые действия** | 1. Проверь наличие `Boot####`: `efibootmgr -v \| grep Boot`.<br>2. Если записи есть, но не в порядке: `efibootmgr -o 0001,0002,0003` (укажи актуальные номера).<br>3. Если записей нет: создай новую → `efibootmgr -c -d /dev/nvme0n1 -p 1 -L "Windows" -l '\EFI\Microsoft\Boot\bootmgfw.efi'`.<br>4. Проверь `Timeout`: `efivar -d -n Timeout-8be4df61...` (должен быть >0 для отладки). |
| **✅ Ожидаемый результат** | `BootOrder` содержит валидные ID, система грузится в нужную ОС. |
| **❌ Неожиданный результат** | Записи создаются, но после перезагрузки исчезают.<br>→ **Действия**: 1) Проверь атрибуты переменной (`efivar -l -v` → ищи `NV`); 2) Возможна коррупция NVRAM → попробуй `Setup → Restore Defaults`; 3) Если не помогает → требуется перепрошивка BIOS (вендорный инструмент). |

### 🔹 Ситуация 2: «Secure Boot: "Operation not permitted" при изменении ключей»
**Симптомы**: Попытка обновить `db`/`dbx` через `efivar` или утилиту вендора выдает `EFI_SECURITY_VIOLATION` или `Access denied`.
**Причина**: Переменная имеет атрибут `TIME_BASED_AUTHENTICATED_WRITE_ACCESS` → требуется подпись ключом, соответствующим `KEK`.

| Этап | Действия |
|------|----------|
| **🎯 Алгоритм выбора инструмента** | 1. `efivar -l \| grep -E 'db\|KEK\|PK'` → 2. Проверка атрибутов (`-v`) → 3. `mokutil` (для MOK-ключей) или вендорная утилита подписи. |
| **⚙️ Рекомендуемые действия** | 1. **Не пытайся записать напрямую** — это не сработает без подписи.<br>2. Для Linux: используй `mokutil --import key.der` → перезагрузка → MOK Manager → enroll.<br>3. Для Windows: используй `SecConfig.exe` (Microsoft) или вендорный `KeyTool`.<br>4. Для тестов: переключи `SetupMode=1` (только если `PK` не установлен!) → тогда можно писать без подписи. |
| **✅ Ожидаемый результат** | Ключ успешно добавлен в `db`/`dbx`, Secure Boot работает с новыми правилами. |
| **❌ Неожиданный результат** | После перезагрузки ключ пропал или система не грузится.<br>→ **Действия**: 1) Загрузись с LiveUSB → проверь `SetupMode`; 2) Если `SetupMode=0` и ключ не работает → восстанови из бэкапа (`efivar -w`); 3) В крайнем случае: `Clear Secure Boot Keys` в BIOS → `Restore Factory Keys`. |

### 🔹 Ситуация 3: «Переменные не видны из Windows, но видны из Linux»
**Симптомы**: `bcdedit /enum firmware` показывает меньше записей, чем `efibootmgr -v` в WSL2/Linux.
**Причина**: Разные уровни доступа: Windows фильтрует переменные без `RT`-атрибута или скрывает "чужие" вендорские.

| Этап | Действия |
|------|----------|
| **🎯 Алгоритм выбора инструмента** | 1. `efivar -l` (полный список) → 2. `GetFirmwareEnvironmentVariable` (PowerShell) → 3. `RWEverything` (чтение регионов, осторожно!). |
| **⚙️ Рекомендуемые действия** | 1. Сравни вывод: `efivar -l \| wc -l` vs `bcdedit /enum firmware \| findstr /c:"identifier"`.<br>2. Проверь атрибуты конкретной переменной: `efivar -v -n Boot0001-8be4df61...` → ищи `RT` (Runtime).<br>3. Если переменной нет `RT` → она видна только до загрузки ОС (это нормально).<br>4. Для полного доступа из Windows: запусти от `NT AUTHORITY\SYSTEM` (через `PsExec -s`). |
| **✅ Ожидаемый результат** | Понимание, какие переменные "живут" в OS, а какие только в firmware. |
| **❌ Неожиданный результат** | Критическая переменная (например, `BootOrder`) имеет атрибуты `NV,BS` но не `RT` → не видна в ОС.<br>→ **Действия**: 1) Не пытайся изменить её из Windows; 2) Используй `efibootmgr` из WinPE/Linux; 3) Если нужно программно → используй `SetFirmwareEnvironmentVariableEx` с правильными флагами. |

### 🔹 Ситуация 4: «После обновления BIOS пропали пользовательские загрузчики»
**Симптомы**: До обновления работали Ventoy/GRUB/Linux, после — только Windows.
**Причина**: Обновление прошивки сбрасывает NVRAM к дефолтным значениям или очищает `db` от сторонних ключей.

| Этап | Действия |
|------|----------|
| **🎯 Алгоритм выбора инструмента** | 1. `efibootmgr -v` (до и после) → 2. Бэкап переменных перед обновлением → 3. Вендорный инструмент для восстановления (`ASUS EZ Flash`, `Dell BIOSConnect`). |
| **⚙️ Рекомендуемые действия** | **Перед обновлением**:<br>1. Сделай бэкап: `for v in $(efivar -l); do efivar -d -n "$v" > "backup/${v//\//_}.bin"; done`.<br>2. Экспортируй `BootOrder` и `Boot####` в текстовый файл.<br>**После обновления**:<br>1. Проверь `BootOrder`: если пуст → восстанови из бэкапа (`efivar -w`).<br>2. Для Ventoy: обнови ключи (`enroll_hash`) или отключи Secure Boot временно. |
| **✅ Ожидаемый результат** | Пользовательские загрузчики возвращаются в меню, дуал-бут работает. |
| **❌ Неожиданный результат** | Бэкап не восстанавливается (ошибка формата/атрибутов).<br>→ **Действия**: 1) Пересоздай записи вручную через `efibootmgr -c`; 2) Для Ventoy: переустанови его на флешку (`Ventoy2Disk.exe --update`); 3) Если Secure Boot блокирует → временно отключи, добавь ключи, включи обратно. |

### 🔹 Ситуация 5: «Timeout=0 → нет меню загрузки, черный экран»
**Симптомы**: Ноутбук сразу грузит Windows, нет возможности выбрать другую ОС или загрузочную флешку.
**Причина**: Переменная `Timeout` установлена в `0` (мгновенный старт первой записи в `BootOrder`).

| Этап | Действия |
|------|----------|
| **🎯 Алгоритм выбора инструмента** | 1. `efivar -d -n Timeout-8be4df61...` → 2. `efibootmgr -t <секунды>` → 3. `bcdedit /timeout <секунды>` (для Windows Boot Manager). |
| **⚙️ Рекомендуемые действия** | 1. Проверь текущее значение: `efivar -d -n Timeout-...` (вернет 4 байта little-endian UINT32).<br>2. Установи 5-10 секунд: `efibootmgr -t 10`.<br>3. Альтернатива из Windows: `bcdedit /set {bootmgr} timeout 10`.<br>4. Для экстренного входа в BIOS: удерживай `Shift` при перезагрузке или нажимай `F2/Del` при старте. |
| **✅ Ожидаемый результат** | При загрузке появляется меню с таймером, можно выбрать устройство. |
| **❌ Неожиданный результат** | Значение не сохраняется после перезагрузки.<br>→ **Действия**: 1) Проверь атрибуты `Timeout` (должен быть `NV`); 2) Возможна защита от записи → попробуй из WinPE; 3) Если не помогает → сбрось NVRAM через BIOS (`Restore Defaults`), затем заново установи `Timeout`. |

### 🔹 Ситуация 6: «Коррупция NVRAM: переменные читаются с ошибками или не читаются»
**Симптомы**: `efivar` выдает `Read error`, `GetFirmwareEnvironmentVariable` возвращает `ERROR_INVALID_FUNCTION`, в логах `dmesg` → `EFIVARFS: CRC mismatch`.
**Причина**: Сбой питания при записи, износ флеша, баг прошивки.

| Этап | Действия |
|------|----------|
| **🎯 Алгоритм выбора инструмента** | 1. `chipsec_util uefi var-list` (только чтение) → 2. `RWEverything` (чтение регионов SPI) → 3. Вендорный Recovery-режим. |
| **⚙️ Рекомендуемые действия** | 1. **Не пытайся записывать** — усугубишь повреждение.<br>2. Попробуй прочитать через `chipsec`: `chipsec_util uefi var-read BootOrder 8be4df61-93ca-11d2-aa0d-00e098032b8c`.<br>3. Если `chipsec` тоже не видит → вероятна физическая коррупция.<br>4. Загрузись в Recovery-режим вендора (например, `Win+B` + Power для HP) → перепрошей BIOS. |
| **✅ Ожидаемый результат** | Переменные читаются, система стабильна. |
| **❌ Неожиданный результат** | После перепрошивки переменные всё равно битые.<br>→ **Действия**: 1) Возможна проблема с регионами SPI (NVRAM region поврежден физически); 2) Требуется программатор (CH341A) для прямой записи дампа; 3) Обратись в сервис — риск "кирпича" высок. |

### 🔹 Ситуация 7: «Конфликт переменных при дуал-буте: одна ОС перезаписывает загрузчик другой»
**Симптомы**: После загрузки Windows перестает видеть Linux (или наоборот), `BootOrder` меняется без ведома пользователя.
**Причина**: ОС автоматически обновляет `BootOrder` при установке обновлений загрузчика.

| Этап | Действия |
|------|----------|
| **🎯 Алгоритм выбора инструмента** | 1. `efibootmgr -v` (сравнение до/после) → 2. `os-prober` (Linux) / `bcdedit` (Win) → 3. Отключение авто-обновления. |
| **⚙️ Рекомендуемые действия** | 1. Зафиксируй текущий `BootOrder`: `efibootmgr > bootorder_before.txt`.<br>2. В Linux: отключи `grub-install` от изменения NVRAM → `GRUB_DISABLE_OS_PROBER=true` в `/etc/default/grub`.<br>3. В Windows: `bcdedit /set {bootmgr} displayorder {current} /addfirst` + отключи авто-обновление через реестр.<br>4. Используй `efibootmgr -A -b XXXX` (активировать) / `-i` (деактивировать) для управления видимостью. |
| **✅ Ожидаемый результат** | `BootOrder` стабилен, обе ОС видны в меню загрузки. |
| **❌ Неожиданный результат** | Одна из ОС перестает грузиться после "фиксации".<br>→ **Действия**: 1) Проверь, не деактивировал ли ты нужную запись (`-i`); 2) Восстанови через `efibootmgr -c` с правильным `--loader` путем; 3) Для надежности: используй `\EFI\BOOT\BOOTX64.EFI` как fallback-загрузчик. |

### 🔹 Ситуация 8: «Переменная не удаляется / "Variable is read-only"»
**Симптомы**: `efibootmgr -b XXXX -B` или `efivar -d` выдает ошибку, переменная остается в списке.
**Причина**: Атрибут `READ_ONLY` (редко), переменная используется системой, или защита от записи в `SetupMode=0`.

| Этап | Действия |
|------|----------|
| **🎯 Алгоритм выбора инструмента** | 1. `efivar -v -n <name-guid>` (проверка атрибутов) → 2. `SetupMode` проверка → 3. Вендорный `KeyTool` или `RWEverything` (эксперт). |
| **⚙️ Рекомендуемые действия** | 1. Проверь атрибуты: если есть `READ_ONLY` → удалить нельзя (это защита прошивки).<br>2. Проверь `SetupMode`: `efivar -d -n SetupMode-...` → если `0` (User Mode), некоторые операции заблокированы.<br>3. Для удаления `Boot####`: сначала убери его из `BootOrder`, потом удаляй.<br>4. Альтернатива: переименуй переменную (создай новую, удали старую), если удаление заблокировано. |
| **✅ Ожидаемый результат** | Лишние записи удалены, `BootOrder` чистый. |
| **❌ Неожиданный результат** | Удаление "успешно", но переменная возвращается после перезагрузки.<br>→ **Действия**: 1) Прошивка автоматически восстанавливает критичные переменные из резервной копии; 2) Требуется отключить авто-восстановление (если возможно) или перепрошить с чистым NVRAM; 3) Оставь как есть, если не мешает — лучше стабильность, чем "чистота". |

[🛡️ Общие правила безопасности для работы с NVRAM]
1. **Чтение > Запись**: Всегда начинай с `efivar -l` / `GetFirmwareEnvironmentVariable`. Записывай только после понимания атрибутов.
2. **Бэкап перед изменениями**: `mkdir nvram_backup && for v in $(efivar -l); do efivar -d -n "$v" > "nvram_backup/${v//\//_}.bin"; done`.
3. **Тестируй в изоляции**: Используй переменные с уникальным GUID (например, `{12345678-1234-1234-1234-123456789012}`) для экспериментов.
4. **Не трогай `PK/KEK/db/dbx` без подписи**: Это может "окирпичить" систему. Для тестов используй `SetupMode=1` (только если `PK` не установлен).
5. **Логгируй всё**: `script nvram_session.log` перед началом сессии → будет что анализировать при сбое.

[RECOMMEND]
1. Создай файл `nvram_recovery.bat` / `nvram_recovery.sh` с командами бэкапа/восстановления `BootOrder` и `Timeout` — держи на Ventoy.
2. Потренируй Ситуацию №1 и №5 на виртуальной машине (OVMF/EDK2) — это безопасно и даст понимание поведения переменных.

[ANTICIPATE]
- "Как узнать GUID переменной, если я знаю только имя?" → Глобальные переменные используют `8BE4DF61-93CA-11d2-00E0-9803-2B8C`. Вендорские — ищи в документации или через `efivar -l \| grep <name>`.
- "Можно ли экспортировать все переменные в человекочитаемый вид?" → Да: `for v in $(efivar -l); do echo "=== $v ==="; efivar -d -n "$v"; done > all_vars.txt`. Но помни: бинарные данные (ключи) так не прочитать — нужен `certutil -decode`.
