### 2. 📘 Руководство: Цикл взаимодействия (Guide)
Локальный Git и GitHub общаются по **клиент-серверной модели**. GitHub не управляет вашим ПК, он только хранит снимки (objects) и указатели (refs).
**Базовый цикл:**
1. `git commit` → снимок сохраняется локально в `.git/objects`.
2. `git push` → Git собирает недостающие объекты, упаковывает их в `packfile`, отправляет на GitHub по HTTP/SSH.
3. GitHub валидирует объекты, обновляет `refs/heads/<branch>` и возвращает статус.
4. `git fetch/pull` → локальный клиент запрашивает с GitHub новые `packfile`, распаковывает в `.git/`, обновляет `refs/remotes/origin/*`.
**Важно:** `origin` — не магия. Это просто алиас для URL в `.git/config`. `git remote -v` показывает его.

### 3. 📋 Шпаргалка: Команды синхронизации (Cheat Sheet)
| Команда | Результат | Когда использовать |
|---|---|---|
| `git remote -v` | Выводит URL `fetch` и `push` | Проверка связи до отправки |
| `git push -u origin <branch>` | Загружает ветку + запоминает связь | При создании новой ветки в репо |
| `git push` | Отправляет новые коммиты на GitHub | Ежедневно, когда `origin` уже привязан |
| `git fetch origin` | Скачивает изменения, НЕ меняя файлы | Безопасная проверка актуальности |
| `git pull` | = `fetch` + `merge` (изменит файлы) | Когда готовы слить серверные правки |
| `git status -sb` | Показывает `ahead/behind origin` | Перед `push`, чтобы оценить расхождение |

### 4. 📖 Мануал: Протоколы и Аутентификация (Reference)
- **HTTPS (`https://github.com/...`)**
  - *Механика:* Стандартный порт 443. Git использует `credential.helper` для кэширования токенов.
  - *Auth:* Пароли отключены в 2021. Требуется **Personal Access Token (PAT)** или **GitHub CLI** (`gh auth login`).
  - *Плюсы:* Работает за корпоративными прокси, проще для первого запуска.
- **SSH (`git@github.com:...`)**
  - *Механика:* Асимметричная криптография. Клиент шифрует challenge приватным ключом, GitHub проверяет публичным ключом из профиля.
  - *Auth:* `ssh-keygen -t ed25519 -C "email"`, публичный ключ добавляется в GitHub Settings → SSH.
  - *Плюсы:* Не требует ввода токена, быстрее, стабильнее для CI/CD и WSL2.
- **Transport Layer:** GitHub использует `smart-http` или `ssh`. Данные передаются дельтами (только изменения). Клиент и сервер согласовывают `capabilities` перед передачей `packfile`.

### 5. 🛡️ Рекомендации: Безопасность и Workflow (Best Practices)
| Аспект | Правило | Обоснование |
|---|---|---|
| **Auth** | Используйте `gh auth login --protocol ssh` или `ed25519` ключи | Токены истекают, SSH ключи стабильнее для WSL2 |
| **Pull Policy** | `git config --global pull.rebase true` | Избегает merge-коммитов, сохраняет линейную историю |
| **Push Safety** | `fetch` → `log` → `pull --rebase` → `push` | Предотвращает `! [rejected]` и конфликты |
| **Force Push** | Запрещён в `main`. Используйте `--force-with-lease` | Проверяет, не изменил ли кто-то сервер после вашего `fetch` |
| **WSL2/Docker** | Генерируйте SSH-ключи **внутри** WSL2 (`~/.ssh/`) | Windows-ключи не пробрасываются автоматически, `ssh-agent` ломается |

🎓 **Ментор: Архитектура/Ловушки**
• **Почему `push` иногда отклоняется?** GitHub требует, чтобы локальная история была *суперсетом* удаленной. Если на сервере появились новые коммиты, Git блокирует `push` для предотвращения потери данных. Решение: `git pull --rebase`, разрешить конфликты → `git push`.
• **`origin` vs `upstream`:** `origin` = ваш форк/репо. `upstream` = оригинальный репозиторий автора. Настройте сразу: `git remote add upstream <original_url>` → `git fetch upstream` → `git rebase upstream/main`.
• **Масштабирование:** Включите на GitHub "Require pull request reviews" и "Require status checks to pass". Это переносит контроль качества из CLI в платформу.



[RECOMMEND]
1. Перейдите на SSH: `ssh-keygen -t ed25519 -C "work@win11"` + `gh auth login --protocol ssh`

3. Добавьте алиас для безопасной синхронизации: `git config --global alias.sync '!git fetch && git status -sb'`

### 2. 📘 Руководство: Стартовая настройка (Guide)
**Шаг 1: Локальный Git (Win11 + WSL2)**
```bash
# 1. Базовая идентификация (обязательно для коммитов)
git config --global user.name "Коллега"
git config --global user.email "work@email.com"

# 2. Дефолтная ветка
git config --global init.defaultBranch main

# 3. Кросс-платформенность (Win11 ↔ WSL2)
git config --global core.autocrlf input  # WSL2: LF в репо, CRLF при checkout в Win
git config --global core.fileMode false  # Игнорировать изменения прав файлов
```

**Шаг 2: Создание репозитория на GitHub**
- Через UI: `+ New repository` → Name → Private/Public → ✅ Add `.gitignore` (Python) → ✅ Add `README` → Create.
- Через CLI: `gh repo create <name> --public --source=. --remote=origin --push` (требует `gh`).

**Шаг 3: Привязка локального репо к GitHub (HTTPS)**
```bash
# Если репо уже существует локально:
git remote add origin https://github.com/<user>/<repo>.git
git branch -M main
git push -u origin main
# Флаг -u запоминает связь: далее достаточно git push / git pull
```

### 3. 📋 Шпаргалка и Конфиги (Cheat Sheet)
| Задача | Команда / Конфиг | Примечание |
|---|---|---|
| **Проверить привязку** | `git remote -v` | Должны быть `fetch` и `push` с `https://github.com/...` |
| **Сменить URL** | `git remote set-url origin https://...` | При переходе с SSH на HTTPS или смене аккаунта |
| **Отвязать remote** | `git remote remove origin` | Безопасно, история не удаляется |
| **HTTPS Credential** | `git config --global credential.helper manager` | Требует установленного Git Credential Manager (GCM) |
| **Альтернатива (кэш)** | `git config --global credential.helper 'cache --timeout=86400'` | Хранит токен 24ч в RAM (WSL2) |

### 4. 📖 Мануал: Механика HTTPS и Аутентификация (Reference)
- **Замена паролей на PAT:** GitHub отключил базовую auth по паролю с 2021. Требуется **Personal Access Token (PAT)** или **GitHub CLI**.
  - Создание: GitHub → Settings → Developer settings → Personal access tokens → Tokens (classic/Fine-grained) → `repo` scope → Generate.
- **Как Git кэширует HTTPS-учетные данные:**
  1. При первом `push/pull` Git запрашивает `Username` и `Password`.
  2. В `Password` вставляется PAT (не логин GitHub!).
  3. `credential.helper` сохраняет пару в OS-хранилище:
     - **Win11:** Windows Credential Manager (GCM)
     - **WSL2:** Может использовать GCM через `/mnt/c/...` или встроенный `cache/store`
- **Архитектура HTTPS-транспорта:** Git упаковывает объекты в `packfile`, отправляет POST-запрос на `/info/refs?service=git-receive-pack`. GitHub валидирует PAT через OAuth-эндпоинт, проверяет права `repo` scope, принимает `packfile`, обновляет `refs/heads/*`. Все по 443/TLS 1.3.

### 5. 🛡️ Рекомендации и Ловушки (Best Practices + Mentor)
| Аспект | Правило | Обоснование / Ловушка |
|---|---|---|
| **Auth в WSL2** | Используйте `gh auth login --protocol https` | `gh` автоматически ставит GCM, настраивает `credential.helper`, избегает ручного ввода PAT |
| **Смена аккаунта** | `git credential-manager uninstall` → reinstall или `git credential-manager clear` | Windows кэширует токены по URL. Без очистки будет `403 Permission denied` |
| **Fine-grained PAT** | Создавайте под конкретный репо с минимальными scopes | Классические PAT с `repo` дают доступ ко всем репозиториям. При компрометации риск выше |
| **WSL2 ↔ Win Credential** | Не смешивайте `cache` и `manager` в `~/.gitconfig` | Конфликт хелперов ведет к `error: cannot spawn ...` или вечным запросам пароля |
| **Масштабирование** | `git config --global credential.https://github.com/username <GH_USER>` | Фиксирует логин для домена, ускоряет auth, исключает ввод username |

🎓 **Ментор: Архитектура & Контекст**
• **Почему PAT вместо пароля?** PAT работает как OAuth-токен. Git передает его в заголовке `Authorization: Basic <base64(user:token)>`. Это позволяет GitHub проверять scopes, вращать ключи и отключать auth без смены пароля аккаунта.
• **Ловушка `! [rejected]`:** Возникает, если remote изменился после вашего `clone/fetch`. Решение: `git fetch origin` → `git rebase origin/main` → `git push`.
• **WSL2 Interop:** Файл `~/.gitconfig` в WSL2 читается только внутри Linux-среды. Windows Git не видит WSL-конфиги. Держите настройки изолированно или используйте `gh` для кросс-платформенной консистентности.



[RECOMMEND]
1. Установите `gh` в WSL2: `sudo apt install gh` → `gh auth login --protocol https --web` (настроит всё автоматически).
2. Зафиксируйте логин в `.gitconfig`: `git config --global credential.https://github.com/username <ваш_ник>`.
3. Проверьте статус auth: `git credential fill` → введите `protocol=https` и `host=github.com` → убедитесь, что токен возвращается.
