[MAIN] 📖 Подробный разбор: что такое UEFITool (практический взгляд)

### 🔹 Простая аналогия
> Представь прошивку как многотомную энциклопедию:
> - **Flash Descriptor** = оглавление всего набора (где какой том лежит).
> - **Regions** = отдельные тома (BIOS, ME, GBE, NVRAM).
> - **Volumes** = главы внутри тома (DXE, PEI, SEC).
> - **Files (FFS)** = статьи в главе (драйверы, приложения, данные).
> - **Sections** = абзацы в статье (код, данные, зависимости).
> 
> **UEFITool** — это умный читатель, который:
> - Показывает структуру в виде дерева.
> - Ищет по ключевым словам (текст, GUID, hex).
> - Вырывает статью для изучения (экспорт `.efi`).
> - Вклеивает исправленную статью обратно (замена).
> - Проверяет, не порвалась ли книга после правки (валидация).

### 🔹 5 правил работы с UEFITool
1. **Всегда работай с копией** [[23]]:
   - Никогда не открывай оригинальный `backup.bin` для модификации.
   - Создай копию: `cp backup.bin mod_work.bin` → работай с ней.

2. **Используй правильную версию** [[35]][[37]]:
   - **Classic (0.28, `old_engine`)**: стабильная замена модулей, но устаревший парсер.
   - **NE (New Engine)**: лучший парсер, поиск по человеческим именам GUID, но замена ещё в разработке.
   - Для модификаций: Classic. Для анализа: NE.

3. **Проверяй после каждой модификации** [[10]][[23]]:
   - `File → Validate image` — ищи ошибки структуры.
   - Сравни размер: если `modded.bin` сильно отличается от оригинала — что-то пошло не так.

4. **Не трогай регионы, которых не понимаешь** [[15]][[42]]:
   - `ME` (Management Engine), `GBE` (сетевой контроллер) — их повреждение может "окирпичить" плату.
   - Модифицируй только `BIOS`-регион, и только те модули, в которых уверен.

5. **Документируй изменения** [[23]][[28]]:
   - Веди лог: какой модуль, из какого образа, на какой заменён, какой GUID.
   - Сохраняй извлечённые `.ffs`/`.efi` файлы в папке `mods/` с понятными именами.

### 🔹 Как читать структуру образа (пример для Vivobook)
```

├─ FV_MAIN (DXE Volume)
│  ├─ CSMCORE (GUID: A062CF1F-8473-4AA3-8793-600BC4FFE9A8)
│  ├─ NvmExpressDxe (GUID: 043B2514-6C9B-4D19-8C89-2E4B4C8F5E6A)  ← NVMe-драйвер
│  ├─ UsbBusDxe (GUID: 2B2F68DA-0CD2-4353-90A2-98C6C3C4E5F1)   ← USB-драйвер
│  └─ ...
├─ FV_SETUP (Setup Volume)
│  ├─ Setup (GUID: ... )  ← настройки BIOS
│  └─ ...
└─ NVRAM Region
   ├─ BootOrder, Boot####, SecureBoot keys  ← переменные
```
**Поиск драйвера**: `Action → Search → Text` → введи `NvmExpress` → дважды кликни по результату → увидишь секции `PE32 Image` (код), `UI` (имя), `Version` (версия).

### 🔍 Этап 1: Анализ структуры (чтение)
| Задача | Действия в UEFITool | Что ищем |
|--------|---------------------|----------|
| **Общая структура** | `File → Open` → `backup.bin` → разверни дерево | Regions, Volumes, ключевые драйверы |
| **Дата сборки** | `Action → Search → Text` → `2025` или GUID `AB56DC60-0057-11DA-A8DB-000102EEE626` → `Hex view` [[1]] | Дата в формате `MM/DD/YYYY` |
| **Версия микрокода** | Вкладка `FIT` (Firmware Interface Table) → ищи `Microcode` | Версии для твоего CPU |
| **Конкретный драйвер** | `Search → Text` → `NvmExpress` или `UsbBus` → разверни найденный файл | Секции: `PE32 Image` (код), `Version` (версия), `UI` (имя) |
| **Переменные (NVRAM)** | Найди регион `NVRAM` → ищи файлы с типом `NVRAM` или именем `VarStore` | `BootOrder`, `SecureBoot`, `Timeout` |

**Пример: поиск и экспорт NVMe-драйвера**:
1. `Action → Search → Text` → введи `NvmExpress`.
2. В результатах найди файл с `Type: DXE driver`.
3. Разверни его → найди секцию `PE32 Image Section`.
4. ПКМ → `Extract body...` → сохрани как `NvmExpress_original.efi`.
5. (Опционально) Открой в HxD → проверь версию в текстовой части.

### ✏️ Этап 2: Модификация (замена модуля)
| Сценарий | Действия | Проверка |
|----------|----------|----------|
| **Замена драйвера на новую версию** | 1. Найди целевой модуль (как выше).<br>2. ПКМ на `PE32 Image Section` → `Replace body...`.<br>3. Выбери новый `.efi` файл (без GUID-заголовка!).<br>4. UEFITool авто-пересчитает контрольную сумму.<br>5. `File → Save image file...` → `work_modified.bin`. | `File → Validate image` → нет ошибок. Размер близок к оригиналу. |
| **Вставка отсутствующего модуля** | 1. Найди целевой Volume (обычно `DXE`).<br>2. Прокрути до последнего модуля в томе.<br>3. ПКМ на последнем модуле → `Insert after` → выбери `.ffs` файл (с GUID!).<br>4. Сохрани образ. | Валидация + проверка, что новый модуль виден в дереве. |
| **Удаление модуля** | 1. Найди модуль.<br>2. ПКМ → `Remove`.<br>3. Сохрани. | ⚠️ Опасно: может сломать зависимости. Только если уверен, что модуль не критичен. |

**⚠️ Критичные предупреждения**:
- **Не заменяй модули с атрибутом `SECT` или `TE` без понимания** — это могут быть критичные компоненты SEC/PEI.
- **Не вставляй модули в середину тома** — UEFITool может некорректно пересчитать смещения. Всегда вставляй `after last`.
- **Сохраняй оригинальные `.ffs`/`.efi`** — если мод не сработает, сможешь откатиться.

### ✅ Этап 3: Валидация и подготовка к записи
```bash
# 1. Валидация в UEFITool
# File → Validate image → нет ошибок "CRC mismatch", "Invalid FFS header"

# 2. Сравнение хешей (оригинал vs мод)
sha256sum original/backup.bin mods/work_modified.bin > logs/hashes.txt

# 3. Тестовая загрузка (если возможно)
# - Запиши мод на второй диск/виртуальную машину
# - Или используй QEMU с OVMF для тестов

# 4. Финальный бэкап перед записью в железо
flashrom -r backups/pre_write_$(date +%Y%m%d).bin --verify
```

### 🔄 Этап 4: Запись (только если всё проверено!)
```bash
# Запись только BIOS-региона (не трогай ME/GBE!)
flashrom -p ch341a_spi -w mods/work_modified.bin --ifd -i bios -N --verify

# Если запись успешна:
echo "✅ Запись завершена. Перезагрузи систему и проверь загрузку."
```

[IF SOFT] 🎓 Ментор: пояснения для beginner
- `.ffs` vs `.efi`: `.ffs` — целый файл с заголовком (GUID, зависимости), `.efi` — только код (тело секции). Для замены тела используй `.efi`, для вставки нового модуля — `.ffs`.
- **Почему вставлять только в конец тома**: У тома есть фиксированный размер. Вставка в середину требует сдвига всех последующих модулей — UEFITool (Classic) делает это не всегда корректно.
- **Как не "окирпичить"**: Никогда не записывай модифицированный образ без: 1) бэкапа оригинала, 2) валидации в UEFITool, 3) верификации при записи (`--verify`).
- **LogoFAIL и безопасность**: Если ищешь уязвимости, начинай с драйверов, парсящих изображения (BMP, JPEG, PNG). Сравнивай их версии с базой уязвимостей (CVE).
- **Масштабирование**: После освоения базовых операций перейди к `UEFIFind` (поиск паттернов в образах) и `chipsec` (аудит безопасности платформы) — это даст глубокое понимание.

если представить UEFITool как python объект, какие атрибуты и методы ты бы реализовал у этого объекта?






```python
class UEFITool:
    """Концептуальная модель UEFITool для анализа, поиска и безопасной модификации UEFI-образов."""

    # ─── КОНСТАНТЫ СПЕЦИФИКАЦИИ ───
    REGIONS = {"FD", "BIOS", "ME", "GBE", "NVRAM"}
    SECTION_TYPES = {"PE32", "TE", "RAW", "VERSION", "UI", "DEPENDENCY", "GUID_DEFINED"}
    FFS_TYPES = {"DRIVER", "APPLICATION", "DXE_CORE", "PEI_CORE", "NVRAM_VAR", "FV_IMAGE"}
    ALIGNMENT = 8  # UEFI FFS требует выравнивания секций

    # ─── АТРИБУТЫ (СОСТОЯНИЕ) ───
    def __init__(self, readonly: bool = True):
        self.raw_image = b""
        self.image_path = None
        self.size_bytes = 0
        
        self.structure_tree: dict = {}      # {region: {volume: {file_id: {sections}}}}
        self.guid_db: dict = {}             # {"{GUID}": "HumanReadableName"}
        self.validation_log: list = []      # Ошибки CRC, битые заголовки, выход за границы
        self.is_modified = False
        self.backup_path = None
        self.readonly = readonly            # Защита от случайных изменений

    # ─── МЕТОДЫ: ЗАГРУЗКА И ПАРСИНГ ───
    def load(self, path: str) -> None:
        """Открытие образа (.bin/.rom/.cap/.fd). Автоматический парсинг FD/FV/FFS."""
        self.image_path = path
        self.raw_image = self._read_binary(path)
        self.size_bytes = len(self.raw_image)
        self.structure_tree = self._parse_fd_regions()
        self._load_guid_db()                # Загрузка GUIDs.txt для человекочитаемых имён
        self.is_modified = False

    def parse_summary(self) -> dict:
        """Быстрый отчёт: регионы, тома, ключевые драйверы, дата сборки."""
        return {
            "regions": list(self.structure_tree.keys()),
            "volumes_count": sum(len(v) for r in self.structure_tree.values() for v in r.values()),
            "dxe_drivers": self._find_files_by_type("DXE_CORE", "DRIVER"),
            "build_date": self._extract_build_date()
        }

    # ─── МЕТОДЫ: ПОИСК ───
    def search_text(self, pattern: str, encoding: str = "utf-16-le") -> list[dict]:
        """Поиск по ASCII/Unicode во всём образе или в выбранных секциях."""
        return self._scan_raw(pattern.encode(encoding))

    def search_guid(self, guid: str) -> list[dict]:
        """Поиск файла/секции по GUID (тип, имя тома, смещение, размер)."""
        return [f for f in self._flatten_files() if f["guid"] == guid.upper()]

    def search_hex(self, pattern: str) -> list[dict]:
        """Поиск байтового паттерна (для версий микрокода, сигнатур драйверов)."""
        return self._scan_raw(bytes.fromhex(pattern.replace(" ", "")))

    # ─── МЕТОДЫ: ИЗВЛЕЧЕНИЕ / МОДИФИКАЦИЯ ───
    def extract_body(self, file_id: str, section_type: str = "PE32") -> bytes:
        """Экспорт тела секции (чистый .efi/.raw без FFS-заголовка)."""
        sec = self._locate_section(file_id, section_type)
        return sec["data"]

    def replace_body(self, file_id: str, section_type: str, new_data: bytes) -> None:
        """Замена тела секции с авто-пересчётом CRC и выравниванием."""
        if self.readonly:
            raise PermissionError("Включён режим только для чтения. Установи readonly=False")
        self._validate_new_section_size(new_data)
        sec = self._locate_section(file_id, section_type)
        sec["data"] = self._align_to_8(new_data)
        self._recalculate_ffs_crc(file_id)
        self.is_modified = True

    def insert_module(self, volume_id: str, ffs_data: bytes, position: str = "end") -> None:
        """Вставка нового .ffs-файла в конец тома (безопасная позиция по умолчанию)."""
        if self.readonly: raise PermissionError("readonly=True")
        if position != "end":
            raise NotImplementedError("Вставка в середину тома может сломать смещения (Classic Engine)")
        self._append_to_volume(volume_id, ffs_data)
        self._rebuild_volume_free_space(volume_id)
        self.is_modified = True

    def remove_module(self, file_id: str) -> None:
        """Удаление FFS-файла с заполнением свободного места 0xFF."""
        if self.readonly: raise PermissionError("readonly=True")
        self._mark_file_deleted(file_id)
        self._compact_volume(self._get_parent_volume(file_id))
        self.is_modified = True

    # ─── МЕТОДЫ: ВАЛИДАЦИЯ И СОХРАНЕНИЕ ───
    def validate(self) -> dict:
        """Проверка целостности: CRC томов/файлов, заголовки FFSv2/v3, границы регионов."""
        errors = []
        for region, volumes in self.structure_tree.items():
            for vol_id, vol_data in volumes.items():
                if not self._check_fv_signature(vol_data): errors.append(f"FV signature broken: {vol_id}")
                for f_id in vol_data["files"]:
                    if not self._check_ffs_integrity(f_id): errors.append(f"FFS CRC mismatch: {f_id}")
        self.validation_log = errors
        return {"valid": len(errors) == 0, "errors": errors}

    def save(self, output_path: str) -> bool:
        """Сборка образа в файл. Только после валидации."""
        if not self.validate()["valid"]:
            raise ValueError("Образ повреждён. Сохранение отменено.")
        self._rebuild_raw_image()
        self._write_binary(output_path, self.raw_image)
        self.backup_path = self.image_path  # Для отката
        self.is_modified = False
        return True

    # ─── ВНУТРЕННИЕ / ЗАЩИТНЫЕ ───
    def _validate_new_section_size(self, data: bytes): ...
    def _recalculate_ffs_crc(self, file_id: str): ...
    def _align_to_8(self, data: bytes) -> bytes: ...
    def _parse_fd_regions(self) -> dict: ...
    def _load_guid_db(self): ...
    def _scan_raw(self, pattern: bytes) -> list: ...
    def _flatten_files(self) -> list: ...
    def _extract_build_date(self) -> str: ...
    def _check_fv_signature(self, vol: dict) -> bool: ...
    def _check_ffs_integrity(self, f_id: str) -> bool: ...
    def _rebuild_raw_image(self) -> None: ...
```

### 📊 Сопоставление: Python-элемент ↔ Реальный UEFITool

| Python-элемент | Аналог в UEFITool | Практическое применение |
|----------------|-------------------|------------------------|
| `readonly=True` | По умолчанию образ открывается в режиме просмотра | Защита от случайного сохранения битого образа |
| `structure_tree` | Дерево слева (Regions → FV → FFS → Sections) | Навигация к `NvmExpressDxe`, `UsbBusDxe`, `Setup` |
| `search_text/guid/hex` | `Action → Search` (Text/GUID/Hex) | Поиск даты сборки, версий микрокода, паттернов LogoFAIL |
| `extract_body` | ПКМ → `Extract body...` | Получение чистого `.efi` для анализа в IDA/Ghidra |
| `replace_body` | ПКМ → `Replace body...` | Обновление драйвера без пересборки тома |
| `insert_module(position="end")` | ПКМ → `Insert after` (на последний файл) | Добавление кастомного модуля без смещения других |
| `validate()` | `File → Validate image` | Проверка CRC/FV-сигнатур перед записью в SPI |
| `save()` | `File → Save image file...` | Финальный экспорт только если `valid=True` |

### ⚙️ Пример рабочего воркфлоу (диагностика → замена драйвера)
```python
tool = UEFITool(readonly=False)
tool.load("backup.bin")

# 1. Анализ
report = tool.parse_summary()
print(f"DXE драйверов: {len(report['dxe_drivers'])}")

# 2. Поиск целевого модуля
hits = tool.search_text("NvmExpress")
target = hits[0]["file_id"]  # Первый найденный файл

# 3. Экспорт оригинала
orig = tool.extract_body(target, "PE32")
open("Nvme_old.efi", "wb").write(orig)

# 4. Замена на исправленную версию
new_driver = open("Nvme_patched.efi", "rb").read()
tool.replace_body(target, "PE32", new_driver)

# 5. Валидация и сохранение
check = tool.validate()
assert check["valid"], f"Ошибки структуры: {check['errors']}"
tool.save("backup_patched.bin")
```

### 🎓 Ментор: почему модель спроектирована так
1. **`readonly=True` по умолчанию** → UEFITool не меняет файл на диске до явного `Save`. В Python это имитируется флагом, чтобы предотвратить `replace_body()` в исследовательских сессиях.
2. **Авто-CRC и выравнивание** → Реальный UEFITool пересчитывает контрольные суммы FFS/FV и дополняет секции до `ALIGNMENT=8`. В модели это скрыто в `_recalculate_*`, чтобы пользователь не думал о бинарной арифметике.
3. **`position="end"` как ограничение** → Classic Engine плохо сдвигает модули в середине тома. Модель явно запрещает `insert before/middle`, чтобы не создавать "тихие" повреждения структуры.
4. **`validate()` перед `save()`** → В UEFITool можно сохранить битый образ, если отключить предупреждения. В модели сохранение блокируется при наличии CRC-ошибок или битых заголовков.
5. **GUID DB** → Соответствует `GUIDs.txt`, который UEFITool NE подгружает автоматически. Без него поиск `043B2514...` превращается в угадывание.

> 💡 *Примечание:* Реальный UEFITool написан на C++/Qt, работает с raw-байтами и не имеет встроенного Python-API. Эта модель — **абстракция рабочего процесса**, помогающая систематизировать действия: `Load → Search → Extract/Replace → Validate → Save`. Держи её как чек-лист при работе с реальным GUI.

[RECOMMEND] Сопоставь методы модели с горячими клавишами UEFITool (`Ctrl+F` поиск, `Ctrl+S` сохранение, `Ctrl+E` экспорт) — это ускорит навигацию на 30-40%.
[ANTICIPATE] Как программно получить список всех GUID в образе без ручного поиска? → `tool.search_guid("*")` (в модели) / в реальном UEFITool: `UEFIExtract report backup.bin > guid_map.json` + `jq '.[].guid'`.

### 🔹 Ситуация 1: «Не могу открыть образ: "Invalid FV signature" / "Unknown format"»
**Симптомы**: UEFITool выдает ошибку при открытии `.bin`/`.rom`, дерево пустое или показывает только `RAW`.
**Причина**: Образ зашифрован/упакован вендором (`.exe`-инсталлятор), это не чистый FD, или файл повреждён.

| Этап | Действия |
|------|----------|
| **🎯 Алгоритм выбора инструмента** | 1. Проверка типа файла: `file backup.bin` (Linux) / HxD (Win) → 2. Если `.exe` → 7-Zip/Universal Extractor → 3. Если зашифрован → искать "чистый" образ на сайте вендора или извлекать через `dd` с известным смещением. |
| **⚙️ Рекомендуемые действия** | 1. Открой файл в HxD: если первые байты `50 4B 03 04` → это ZIP (переименуй в `.zip` и распакуй).<br>2. Если `MZ` в начале → это `.exe`-инсталлятор: попробуй открыть 7-Zip'ом или запусти с ключом `/extract`.<br>3. Ищи в образе сигнатуру `_FVH` (Firmware Volume Header): `Search → Hex → 5F 46 56 48`.<br>4. Если нашёл → вычисли смещение, обрежь заголовок: `dd if=original.bin of=clean.bin bs=1 skip=OFFSET`. |
| **✅ Ожидаемый результат** | UEFITool открывает `clean.bin`, показывает дерево Regions → FV → FFS. |
| **❌ Неожиданный результат** | Сигнатура `_FVH` не найдена, образ выглядит как случайные данные.<br>→ **Действия**: 1) Возможна компрессия/шифрование (редко для consumer-плат); 2) Попробуй другой образ (официальный с сайта вендора); 3) Если это дамп с программатора — проверь, не считал ли ты пустой чип (контакт, напряжение). |

### 🔹 Ситуация 2: «Поиск по тексту не находит известный драйвер»
**Симптомы**: `Action → Search → Text → "NvmExpress"` возвращает 0 результатов, хотя драйвер точно есть в прошивке.
**Причина**: Текст закодирован в Unicode (UTF-16LE), поиск ведётся только по ASCII, или строка разбита выравниванием.

| Этап | Действия |
|------|----------|
| **🎯 Алгоритм выбора инструмента** | 1. Попробовать поиск по Unicode: `Search → Text → Encoding: UTF-16LE` → 2. Поиск по GUID (если известен) → 3. Поиск по hex-паттерну версии драйвера. |
| **⚙️ Рекомендуемые действия** | 1. В окне поиска выбери `Encoding: UTF-16LE` (малоэндиян) → введи `NvmExpress` → Search.<br>2. Если не помогло: найди GUID драйвера в базе (`GUIDs.txt` или онлайн) → `Search → GUID` → вставь `043B2514-6C9B-4D19-8C89-2E4B4C8F5E6A`.<br>3. Альтернатива: открой образ в HxD, найди ASCII-строку, скопируй её hex-представление → `Search → Hex` в UEFITool. |
| **✅ Ожидаемый результат** | Найден файл типа `DXE Driver` с нужным именем, можно экспортировать/анализировать. |
| **❌ Неожиданный результат** | Поиск по GUID тоже не даёт результатов.<br>→ **Действия**: 1) Возможно, драйвер имеет другое имя (проверь `UEFITool → View → Show GUIDs`); 2) Образ может быть для другой архитектуры (ARM vs x64) — проверь `parse_summary()`; 3) Попробуй поискать по части имени (`Nvm`, `Express`) с включённым `Case insensitive`. |

### 🔹 Ситуация 3: «Replace body: после сохранения образ не грузится»
**Симптомы**: Заменил `NvmExpressDxe` на новую версию, сохранил, записал в чип → система зависает на `DXE` или выдаёт `Security violation`.
**Причина**: Новый модуль несовместим по архитектуре/версии UEFI, не подписан (Secure Boot), или нарушены зависимости (Depex).

| Этап | Действия |
|------|----------|
| **🎯 Алгоритм выбора инструмента** | 1. Сравнить оригинал и новый модуль в HxD/IDA → 2. Проверить подпись: `sigcheck -a new.efi` (Sysinternals) → 3. Проверить Depex-секцию в UEFITool. |
| **⚙️ Рекомендуемые действия** | **Перед заменой**:<br>1. Убедись, что новый `.efi` той же архитектуры (x64) и версии UEFI (2.x).<br>2. Проверь секции: в оригинале могут быть `UI`, `Version`, `Depex` — если в новом их нет, UEFITool не добавит их автоматически.<br>3. Для Secure Boot: новый модуль должен быть подписан ключом, присутствующим в `db`, или отключи Secure Boot для теста.<br>**После сбоя**:<br>1. Верни оригинал из бэкапа (`flashrom -w backup.bin`).<br>2. Проанализируй лог POST-кодов: код `0x5x-0x7x` = ошибка в DXE-драйвере. |
| **✅ Ожидаемый результат** | Модифицированный образ проходит валидацию, система грузится, драйвер работает. |
| **❌ Неожиданный результат** | Даже с оригинальным модулем система не грузится после записи.<br>→ **Действия**: 1) Возможна ошибка при записи (`flashrom --verify` не прошёл); 2) Проверь целостность образа: `UEFITool → Validate`; 3) Если образ битый — восстанови из аппаратного бэкапа (программатор). |

### 🔹 Ситуация 4: «После Save размер образа изменился на >1 КБ»
**Симптомы**: Оригинальный `backup.bin` = 16 777 216 байт, `modded.bin` = 16 778 432 байт.
**Причина**: UEFITool (Classic) может некорректно пересчитать свободное пространство в томе или добавить паддинги при вставке.

| Этап | Действия |
|------|----------|
| **🎯 Алгоритм выбора инструмента** | 1. Сравнить в HxD: `Search → Find difference` → 2. Проверить `Validate` в UEFITool → 3. Использовать `UEFIFind`/`UEFIExtract` для анализа структуры. |
| **⚙️ Рекомендуемые действия** | 1. **Не записывай** образ с изменённым размером — прошивка может не принять его (размер чипа фиксирован).<br>2. В HxD найди, где именно добавились байты: обычно в конце тома (`FV`) как `0xFF`-паддинг.<br>3. Если разница только в паддинге — можно обрезать: `dd if=modded.bin of=final.bin bs=1 count=ORIGINAL_SIZE`.<br>4. Альтернатива: используй UEFITool **NE** (New Engine) — он лучше сохраняет структуру. |
| **✅ Ожидаемый результат** | Размер `final.bin` совпадает с оригиналом, валидация проходит. |
| **❌ Неожиданный результат** | Разница не в паддинге, а в середине образа (смещения сдвинуты).<br>→ **Действия**: 1) Отмени модификацию, начни заново; 2) Попробуй вставить модуль строго в конец тома (`Insert after` на последний файл); 3) Если критично — используй `dd` для ручной вставки по смещению (только для экспертов!). |

### 🔹 Ситуация 5: «Не могу найти переменные NVRAM (BootOrder, SecureBoot)»
**Симптомы**: В дереве нет региона `NVRAM` или файлов с переменными, хотя они должны быть.
**Причина**: Переменные хранятся в отдельном регионе (`NVRAM`), который может быть не включён в дамп, или они в `FV_NVRAM` с нестандартным GUID.

| Этап | Действия |
|------|----------|
| **🎯 Алгоритм выбора инструмента** | 1. Проверить `Flash Descriptor`: есть ли регион `NVRAM` → 2. Поиск по типу файла: `FFS Type: NVRAM_VAR` → 3. Поиск по имени переменной: `Search → Text → "BootOrder"`. |
| **⚙️ Рекомендуемые действия** | 1. Разверни `Flash Descriptor` → проверь, что регион `NVRAM` имеет ненулевой размер.<br>2. Если регион есть, но пуст: переменные могут храниться в `FV_MAIN` как файлы типа `NVRAM_VAR` → `View → Filter → Show NVRAM_VAR`.<br>3. Поиск по тексту: `BootOrder`, `Timeout`, `SecureBoot` (учти Unicode!).<br>4. Если не найдено: возможно, дамп сделан без региона NVRAM (некоторые программаторы/утилиты пропускают его). |
| **✅ Ожидаемый результат** | Найдены файлы с переменными, можно экспортировать для анализа (`efivar`-формат). |
| **❌ Неожиданный результат** | Регион `NVRAM` есть, но файлы не читаются (битый заголовок).<br>→ **Действия**: 1) Возможна коррупция NVRAM в самом чипе; 2) Попробуй прочитать переменные из работающей системы: `efivar -l` / `GetFirmwareEnvironmentVariable`; 3) Для восстановления: используй `RWEverything` (чтение) + вендорный `Setup → Restore Defaults`. |

### 🔹 Ситуация 6: «Validate показывает ошибки после модификации»
**Симптомы**: `File → Validate image` выдаёт `CRC mismatch`, `Invalid FFS header`, `Free space calculation error`.
**Причина**: Ручная модификация нарушила структуру: не пересчитан CRC, неверное выравнивание, выход за границы тома.

| Этап | Действия |
|------|----------|
| **🎯 Алгоритм выбора инструмента** | 1. Читать ошибки валидации по порядку → 2. Проверить модифицированный модуль в `Hex view` → 3. Сравнить с оригиналом в Hезд. |
| **⚙️ Рекомендуемые действия** | 1. **Не сохраняй** образ с ошибками валидации.<br>2. Найди в логе имя файла/тома с ошибкой → перейди к нему в дереве.<br>3. Проверь секции: `CRC32` должен быть пересчитан (UEFITool делает это авто, но если менял вручную — нет).<br>4. Проверь выравнивание: размер секции должен быть кратен 8 байтам.<br>5. Если ошибка в `Free space`: возможно, вставленный модуль не влез в том → удали его, попробуй вставить в другой том или сжать оригинал. |
| **✅ Ожидаемый результат** | `Validate` возвращает `valid: true`, можно сохранять. |
| **❌ Неожиданный результат** | Ошибки остаются после отката изменений.<br>→ **Действия**: 1) Возможно, исходный образ уже был повреждён; 2) Попробуй открыть оригинал в другой версии UEFITool (Classic ↔ NE); 3) Если образ критичен — восстанови из аппаратного бэкапа. |

### 🔹 Ситуация 7: «GUID показывается как "Unknown", не могу найти по имени»
**Симптомы**: В дереве файл имеет имя `{12345678-1234-1234-1234-123456789012}`, поиск по человеческому имени не работает.
**Причина**: База GUID (`GUIDs.txt`) не загружена, или этот GUID вендорский/кастомный, отсутствует в публичных базах.

| Этап | Действия |
|------|----------|
| **🎯 Алгоритм выбора инструмента** | 1. Проверить, загружена ли база: `View → GUID Database → Load` → 2. Поиск GUID в интернете: `github.com/LongSoft/UEFITool GUIDs.txt` → 3. Анализ секций файла для определения назначения. |
| **⚙️ Рекомендуемые действия** | 1. Загрузи актуальную базу: `UEFITool → View → GUID Database → Load from file` (скачай с [github.com/LongSoft/UEFITool](https://github.com/LongSoft/UEFITool)).<br>2. Если GUID всё равно unknown: скопируй его, поищи в `google: "{GUID} UEFI"` или `edk2-staging`.<br>3. Проанализируй секции: если есть `UI Section` с текстом — это имя; если `PE32` с импортами `gBS->InstallProtocolInterface` — это драйвер протокола. |
| **✅ Ожидаемый результат** | Файл получает человекочитаемое имя, легче ориентироваться в структуре. |
| **❌ Неожиданный результат** | GUID действительно кастомный, информации нет.<br>→ **Действия**: 1) Не модифицируй неизвестные модули — риск сломать зависимость; 2) Экспортируй, проанализируй в IDA/Ghidra (если нужно); 3) Оставь комментарий в логе: `# Unknown GUID {xxx} — не трогать`. |

### 🔹 Ситуация 8: «Сравнение двух версий прошивки: что изменилось?»
**Симптомы**: Есть `old.bin` и `new.bin` от вендора, нужно понять, что обновили (микрокод, драйверы, уязвимости).
**Причина**: Вендоры редко публикуют changelog с деталями, нужно сравнивать бинарно.

| Этап | Действия |
|------|----------|
| **🎯 Алгоритм выбора инструмента** | 1. Открыть оба образа в двух окнах UEFITool → 2. Использовать `UEFIFind`/`UEFIExtract` для генерации отчётов → 3. Сравнить отчёты через `diff`/`Beyond Compare`. |
| **⚙️ Рекомендуемые действия** | 1. В UEFITool: `File → Export → Report` для каждого образа → получишь список файлов с GUID/смещениями.<br>2. Сравни отчёты: `diff old_report.txt new_report.txt` → найди добавленные/удалённые GUID.<br>3. Для ключевых модулей (микрокод, `NvmExpressDxe`, `SecurityPkg`): экспортируй `.efi` из обоих образов → сравни в Hезд (`Find differences`).<br>4. Проверь FIT-таблицу: `View → FIT` → сравни версии микрокода, даты. |
| **✅ Ожидаемый результат** | Список изменённых модулей, понимание, что обновили (например, `Microcode: 0xAA → 0xBB`, `NvmExpressDxe: v1.2 → v1.3`). |
| **❌ Неожиданный результат** | Отчёты идентичны, но образы разные по хешу.<br>→ **Действия**: 1) Возможны изменения в паддинге/выравнивании (не критично); 2) Проверь `RAW`-секции: возможно, изменились данные без изменения структуры; 3) Используй бинарное сравнение: `cmp -l old.bin new.bin | head -20`. |

### 🔹 Ситуация 9: «Экспортированный .efi не работает при обратной вставке»
**Симптомы**: Извлёк `bootmgfw.efi` через `Extract body`, отредактировал, вставил обратно → система не грузится.
**Причина**: При экспорте/вставке потерялись зависимости (секции `Depex`, `UI`, `Version`), или изменилось выравнивание.

| Этап | Действия |
|------|----------|
| **🎯 Алгоритм выбора инструмента** | 1. Сравнить оригинальный и модифицированный FFS-файл в Hезд → 2. Проверить наличие всех секций в UEFITool → 3. Использовать `Replace body` вместо ручного редактирования заголовка. |
| **⚙️ Рекомендуемые действия** | **Правильный воркфлоу**:<br>1. Найди файл → разверни → найди секцию `PE32 Image`.<br>2. ПКМ на `PE32 Image` → `Extract body...` → получишь чистый `.efi` (код).<br>3. Отредактируй `.efi` (патч, рекомпиляция).<br>4. Вернись к тому же файлу в UEFITool → ПКМ на `PE32 Image` → `Replace body...` → выбери новый `.efi`.<br>5. UEFITool авто-пересчитает заголовок и CRC.<br>**Если уже сломал**:<br>1. Верни оригинальный `.efi` через `Replace body`.<br>2. Если не помогло — восстанови весь файл из бэкапа. |
| **✅ Ожидаемый результат** | Модифицированный модуль встраивается без ошибок, система грузится. |
| **❌ Неожиданный результат** | Даже с оригинальным `.efi` после `Replace body` возникают ошибки.<br>→ **Действия**: 1) Возможна проблема с выравниванием: убедись, что новый `.efi` имеет размер, кратный 4/8 байтам; 2) Проверь, не изменил ли ты точку входа (`AddressOfEntryPoint`); 3) Если критично — не модифицируй загрузчик, используй внешний загрузчик (Ventoy). |

[🛡️ Общие правила безопасности при работе с UEFITool]
1. **readonly по умолчанию**: Открывай образы в режиме просмотра, включай модификацию только когда готов сохранять.
2. **Бэкап перед каждым действием**: `cp work.bin work_$(date +%s).bin` — откат за 5 секунд.
3. **Валидация — обязательный шаг**: Никогда не записывай в железо образ без `Validate → valid: true`.
4. **Не трогай неизвестное**: Если GUID unknown и нет документации — не модифицируй.
5. **Тестируй на виртуалке**: QEMU с OVMF — безопасный полигон для проверки модифицированных образов.

[RECOMMEND]
1. Создай шаблон `uefi_session.sh`/`.bat` с командами: бэкап, запуск UEFITool, валидация, логирование.

[ANTICIPATE]
- "Как автоматически извлечь все .efi из образа?" → `UEFIExtract backup.bin report > map.json` + скрипт на `jq` для парсинга и `dd` для извлечения по смещениям.
- "Можно ли патчить образ без UEFITool?" → Да, через `hexedit` + знание структуры, но риск ошибки ×10. UEFITool берёт на себя CRC/выравнивание — это стоит использования.
