### 1. Исследование форматов и порядок подачи
| Формат | Цель | Структура | Аудитория | Порядок в обучении |
|--------|------|-----------|-----------|-------------------|
| **Руководство (Guide/Tutorial)** | Достичь результата шаг за шагом | Нарратив, цель → действие → проверка | Новичок | 1-й этап (контекст + практика) |
| **Шпаргалка (Cheat Sheet)** | Быстрый синтаксис без поиска | Таблицы, команды, флаги, примеры | Все уровни | Параллельно с практикой |
| **Мануал (Reference)** | Точная спецификация, все флаги | Иерархия/алфавит, вход/выход/ошибки | Средний/Про | Справочно, при углублении |
| **Рекомендации (Best Practices)** | Архитектура, безопасность, масштабируемость | Принципы, антипаттерны, кейсы | Средний/Про | После освоения базового workflow |

**Вывод:** Порядок подачи для новичка: `Руководство → Шпаргалка → Мануал (по мере запроса) → Рекомендации`. Git объясняется именно в этой последовательности.

### 2. Архитектура Git (First Principles)
Git — распределённая система контроля версий. Данные не "хранятся в файлах", а представляют **ориентированный ациклический граф коммитов**.
**4 зоны (обязательно для понимания команд):**
1. `Working Directory` — ваши файлы на диске (можно менять, ломать, сохранять).
2. `Staging Area (Index)` — буфер. Здесь вы формируете, что войдёт в следующий коммит.
3. `Local Repository` — скрытая папка `.git/`. Содержит полную историю, ветки, теги. Работает оффлайн.
4. `Remote Repository` (GitHub/GitLab/Bitbucket) — общий сервер. Синхронизация по сети.

### 3. Команды по Workflow (Guide + Cheat Sheet)

#### 🟢 Инициализация и подключение
```bash
git init                  # Создать .git в текущей папке (начало трекинга)
git clone <url>           # Скачать репозиторий + настроить origin (обычно 1-й шаг)
git remote -v             # Показать подключенные удаленные репозитории
```

#### 🟡 Отслеживание состояния и подготовка
```bash
git status                # Что изменено? Что в staging? (запускать перед каждой командой)
git add <file|path|->     # Перенести изменения в Staging (. = все, -u = только измененные)
git diff                  # Изменения в Working Dir vs Staging
git diff --staged         # Изменения в Staging vs последний коммит
```

#### 🔴 Фиксация истории
```bash
git commit -m "fix: auth token leak"  # Создать снимок состояния из Staging
git log --oneline --graph             # Визуализировать цепочку коммитов
git restore <file>                    # Откатить файл до состояния Staging/HEAD
git reset --soft HEAD~1               # Отменить последний коммит, но сохранить изменения в Staging
```

#### 🟣 Ветвление и слияние
```bash
git branch                  # Список локальных веток
git switch -c <name>        # Создать и перейти в ветку (современная замена checkout -b)
git merge <branch>          # Влить ветку в текущую (fast-forward или merge commit)
git rebase <branch>         # Переписать историю, наложив коммиты сверху (чище лог)
```

#### 🔵 Синхронизация с Remote
```bash
git fetch                   # Скачать изменения, НЕ меняя Working Dir (безопасно)
git pull                    # fetch + merge (или rebase если настроено)
git push                    # Отправить локальные коммиты на сервер
```

### 4. Специфика вашего стека (Win11 + WSL2 + Docker + VSCode)
| Проблема | Причина | Решение |
|----------|---------|---------|
| `\r\n` vs `\n` | Win использует CRLF, Git/WSL ожидает LF | `git config --global core.autocrlf input` (в WSL2) |
| Права файлов | Git помнит `chmod`, Docker/Win меняет при маппинге | `git config --global core.fileMode false` |
| Docker volumes + Git | `.git` внутри контейнера ломает sync из-за inode/permissions | Монтируйте только проект, `.git` держите в WSL2, используйте `.dockerignore` |
| VSCode интеграция | Терминал VSCode может запускать `cmd` вместо `wsl` | Настройки → `Terminal > Integrated > Default Profile: Linux (WSL)` |

### 5. Рекомендации и ловушки (Best Practices)
• **Атомарные коммиты:** 1 коммит = 1 логическая задача. Не смешивайте `fix` и `refactor`.
• **Конвенции имён:** `type(scope): description` (Conventional Commits). Упрощает `git log` и CI.
• **Безопасность:** 
  - `git push --force` → перезаписывает историю на сервере. Используйте `--force-with-lease` (проверяет, не изменил ли кто-то сервер).
  - `git reset --hard` → удаляет изменения безвозвратно. Восстановить сложно (`git reflog`).
• **Git + Python/WSL:** Создавайте `.gitignore` через `gitignore.io api python,windows,vscode`. Никогда не коммитьте `.venv/`, `__pycache__/`, `.env`.
• **Масштабирование:** При >5 разработчиках переходите на `trunk-based development` + `pull requests` + автоматический `git rebase` перед мерджем.
