### 🔹 Ситуация 1: «Не могу открыть образ: "Invalid FV signature" / "Unknown format"»
**Симптомы**: UEFITool выдает ошибку при открытии `.bin`/`.rom`, дерево пустое или показывает только `RAW`.
**Причина**: Образ зашифрован/упакован вендором (`.exe`-инсталлятор), это не чистый FD, или файл повреждён.

| Этап | Действия |
|------|----------|
| **🎯 Алгоритм выбора инструмента** | 1. Проверка типа файла: `file backup.bin` (Linux) / HxD (Win) → 2. Если `.exe` → 7-Zip/Universal Extractor → 3. Если зашифрован → искать "чистый" образ на сайте вендора или извлекать через `dd` с известным смещением. |
| **⚙️ Рекомендуемые действия** | 1. Открой файл в HxD: если первые байты `50 4B 03 04` → это ZIP (переименуй в `.zip` и распакуй).<br>2. Если `MZ` в начале → это `.exe`-инсталлятор: попробуй открыть 7-Zip'ом или запусти с ключом `/extract`.<br>3. Ищи в образе сигнатуру `_FVH` (Firmware Volume Header): `Search → Hex → 5F 46 56 48`.<br>4. Если нашёл → вычисли смещение, обрежь заголовок: `dd if=original.bin of=clean.bin bs=1 skip=OFFSET`. |
| **✅ Ожидаемый результат** | UEFITool открывает `clean.bin`, показывает дерево Regions → FV → FFS. |
| **❌ Неожиданный результат** | Сигнатура `_FVH` не найдена, образ выглядит как случайные данные.<br>→ **Действия**: 1) Возможна компрессия/шифрование (редко для consumer-плат); 2) Попробуй другой образ (официальный с сайта вендора); 3) Если это дамп с программатора — проверь, не считал ли ты пустой чип (контакт, напряжение). |

### 🔹 Ситуация 2: «Поиск по тексту не находит известный драйвер»
**Симптомы**: `Action → Search → Text → "NvmExpress"` возвращает 0 результатов, хотя драйвер точно есть в прошивке.
**Причина**: Текст закодирован в Unicode (UTF-16LE), поиск ведётся только по ASCII, или строка разбита выравниванием.

| Этап | Действия |
|------|----------|
| **🎯 Алгоритм выбора инструмента** | 1. Попробовать поиск по Unicode: `Search → Text → Encoding: UTF-16LE` → 2. Поиск по GUID (если известен) → 3. Поиск по hex-паттерну версии драйвера. |
| **⚙️ Рекомендуемые действия** | 1. В окне поиска выбери `Encoding: UTF-16LE` (малоэндиян) → введи `NvmExpress` → Search.<br>2. Если не помогло: найди GUID драйвера в базе (`GUIDs.txt` или онлайн) → `Search → GUID` → вставь `043B2514-6C9B-4D19-8C89-2E4B4C8F5E6A`.<br>3. Альтернатива: открой образ в HxD, найди ASCII-строку, скопируй её hex-представление → `Search → Hex` в UEFITool. |
| **✅ Ожидаемый результат** | Найден файл типа `DXE Driver` с нужным именем, можно экспортировать/анализировать. |
| **❌ Неожиданный результат** | Поиск по GUID тоже не даёт результатов.<br>→ **Действия**: 1) Возможно, драйвер имеет другое имя (проверь `UEFITool → View → Show GUIDs`); 2) Образ может быть для другой архитектуры (ARM vs x64) — проверь `parse_summary()`; 3) Попробуй поискать по части имени (`Nvm`, `Express`) с включённым `Case insensitive`. |

### 🔹 Ситуация 3: «Replace body: после сохранения образ не грузится»
**Симптомы**: Заменил `NvmExpressDxe` на новую версию, сохранил, записал в чип → система зависает на `DXE` или выдаёт `Security violation`.
**Причина**: Новый модуль несовместим по архитектуре/версии UEFI, не подписан (Secure Boot), или нарушены зависимости (Depex).

| Этап | Действия |
|------|----------|
| **🎯 Алгоритм выбора инструмента** | 1. Сравнить оригинал и новый модуль в HxD/IDA → 2. Проверить подпись: `sigcheck -a new.efi` (Sysinternals) → 3. Проверить Depex-секцию в UEFITool. |
| **⚙️ Рекомендуемые действия** | **Перед заменой**:<br>1. Убедись, что новый `.efi` той же архитектуры (x64) и версии UEFI (2.x).<br>2. Проверь секции: в оригинале могут быть `UI`, `Version`, `Depex` — если в новом их нет, UEFITool не добавит их автоматически.<br>3. Для Secure Boot: новый модуль должен быть подписан ключом, присутствующим в `db`, или отключи Secure Boot для теста.<br>**После сбоя**:<br>1. Верни оригинал из бэкапа (`flashrom -w backup.bin`).<br>2. Проанализируй лог POST-кодов: код `0x5x-0x7x` = ошибка в DXE-драйвере. |
| **✅ Ожидаемый результат** | Модифицированный образ проходит валидацию, система грузится, драйвер работает. |
| **❌ Неожиданный результат** | Даже с оригинальным модулем система не грузится после записи.<br>→ **Действия**: 1) Возможна ошибка при записи (`flashrom --verify` не прошёл); 2) Проверь целостность образа: `UEFITool → Validate`; 3) Если образ битый — восстанови из аппаратного бэкапа (программатор). |

### 🔹 Ситуация 4: «После Save размер образа изменился на >1 КБ»
**Симптомы**: Оригинальный `backup.bin` = 16 777 216 байт, `modded.bin` = 16 778 432 байт.
**Причина**: UEFITool (Classic) может некорректно пересчитать свободное пространство в томе или добавить паддинги при вставке.

| Этап | Действия |
|------|----------|
| **🎯 Алгоритм выбора инструмента** | 1. Сравнить в HxD: `Search → Find difference` → 2. Проверить `Validate` в UEFITool → 3. Использовать `UEFIFind`/`UEFIExtract` для анализа структуры. |
| **⚙️ Рекомендуемые действия** | 1. **Не записывай** образ с изменённым размером — прошивка может не принять его (размер чипа фиксирован).<br>2. В HxD найди, где именно добавились байты: обычно в конце тома (`FV`) как `0xFF`-паддинг.<br>3. Если разница только в паддинге — можно обрезать: `dd if=modded.bin of=final.bin bs=1 count=ORIGINAL_SIZE`.<br>4. Альтернатива: используй UEFITool **NE** (New Engine) — он лучше сохраняет структуру. |
| **✅ Ожидаемый результат** | Размер `final.bin` совпадает с оригиналом, валидация проходит. |
| **❌ Неожиданный результат** | Разница не в паддинге, а в середине образа (смещения сдвинуты).<br>→ **Действия**: 1) Отмени модификацию, начни заново; 2) Попробуй вставить модуль строго в конец тома (`Insert after` на последний файл); 3) Если критично — используй `dd` для ручной вставки по смещению (только для экспертов!). |

### 🔹 Ситуация 5: «Не могу найти переменные NVRAM (BootOrder, SecureBoot)»
**Симптомы**: В дереве нет региона `NVRAM` или файлов с переменными, хотя они должны быть.
**Причина**: Переменные хранятся в отдельном регионе (`NVRAM`), который может быть не включён в дамп, или они в `FV_NVRAM` с нестандартным GUID.

| Этап | Действия |
|------|----------|
| **🎯 Алгоритм выбора инструмента** | 1. Проверить `Flash Descriptor`: есть ли регион `NVRAM` → 2. Поиск по типу файла: `FFS Type: NVRAM_VAR` → 3. Поиск по имени переменной: `Search → Text → "BootOrder"`. |
| **⚙️ Рекомендуемые действия** | 1. Разверни `Flash Descriptor` → проверь, что регион `NVRAM` имеет ненулевой размер.<br>2. Если регион есть, но пуст: переменные могут храниться в `FV_MAIN` как файлы типа `NVRAM_VAR` → `View → Filter → Show NVRAM_VAR`.<br>3. Поиск по тексту: `BootOrder`, `Timeout`, `SecureBoot` (учти Unicode!).<br>4. Если не найдено: возможно, дамп сделан без региона NVRAM (некоторые программаторы/утилиты пропускают его). |
| **✅ Ожидаемый результат** | Найдены файлы с переменными, можно экспортировать для анализа (`efivar`-формат). |
| **❌ Неожиданный результат** | Регион `NVRAM` есть, но файлы не читаются (битый заголовок).<br>→ **Действия**: 1) Возможна коррупция NVRAM в самом чипе; 2) Попробуй прочитать переменные из работающей системы: `efivar -l` / `GetFirmwareEnvironmentVariable`; 3) Для восстановления: используй `RWEverything` (чтение) + вендорный `Setup → Restore Defaults`. |

### 🔹 Ситуация 6: «Validate показывает ошибки после модификации»
**Симптомы**: `File → Validate image` выдаёт `CRC mismatch`, `Invalid FFS header`, `Free space calculation error`.
**Причина**: Ручная модификация нарушила структуру: не пересчитан CRC, неверное выравнивание, выход за границы тома.

| Этап | Действия |
|------|----------|
| **🎯 Алгоритм выбора инструмента** | 1. Читать ошибки валидации по порядку → 2. Проверить модифицированный модуль в `Hex view` → 3. Сравнить с оригиналом в Hезд. |
| **⚙️ Рекомендуемые действия** | 1. **Не сохраняй** образ с ошибками валидации.<br>2. Найди в логе имя файла/тома с ошибкой → перейди к нему в дереве.<br>3. Проверь секции: `CRC32` должен быть пересчитан (UEFITool делает это авто, но если менял вручную — нет).<br>4. Проверь выравнивание: размер секции должен быть кратен 8 байтам.<br>5. Если ошибка в `Free space`: возможно, вставленный модуль не влез в том → удали его, попробуй вставить в другой том или сжать оригинал. |
| **✅ Ожидаемый результат** | `Validate` возвращает `valid: true`, можно сохранять. |
| **❌ Неожиданный результат** | Ошибки остаются после отката изменений.<br>→ **Действия**: 1) Возможно, исходный образ уже был повреждён; 2) Попробуй открыть оригинал в другой версии UEFITool (Classic ↔ NE); 3) Если образ критичен — восстанови из аппаратного бэкапа. |

### 🔹 Ситуация 7: «GUID показывается как "Unknown", не могу найти по имени»
**Симптомы**: В дереве файл имеет имя `{12345678-1234-1234-1234-123456789012}`, поиск по человеческому имени не работает.
**Причина**: База GUID (`GUIDs.txt`) не загружена, или этот GUID вендорский/кастомный, отсутствует в публичных базах.

| Этап | Действия |
|------|----------|
| **🎯 Алгоритм выбора инструмента** | 1. Проверить, загружена ли база: `View → GUID Database → Load` → 2. Поиск GUID в интернете: `github.com/LongSoft/UEFITool GUIDs.txt` → 3. Анализ секций файла для определения назначения. |
| **⚙️ Рекомендуемые действия** | 1. Загрузи актуальную базу: `UEFITool → View → GUID Database → Load from file` (скачай с [github.com/LongSoft/UEFITool](https://github.com/LongSoft/UEFITool)).<br>2. Если GUID всё равно unknown: скопируй его, поищи в `google: "{GUID} UEFI"` или `edk2-staging`.<br>3. Проанализируй секции: если есть `UI Section` с текстом — это имя; если `PE32` с импортами `gBS->InstallProtocolInterface` — это драйвер протокола. |
| **✅ Ожидаемый результат** | Файл получает человекочитаемое имя, легче ориентироваться в структуре. |
| **❌ Неожиданный результат** | GUID действительно кастомный, информации нет.<br>→ **Действия**: 1) Не модифицируй неизвестные модули — риск сломать зависимость; 2) Экспортируй, проанализируй в IDA/Ghidra (если нужно); 3) Оставь комментарий в логе: `# Unknown GUID {xxx} — не трогать`. |

### 🔹 Ситуация 8: «Сравнение двух версий прошивки: что изменилось?»
**Симптомы**: Есть `old.bin` и `new.bin` от вендора, нужно понять, что обновили (микрокод, драйверы, уязвимости).
**Причина**: Вендоры редко публикуют changelog с деталями, нужно сравнивать бинарно.

| Этап | Действия |
|------|----------|
| **🎯 Алгоритм выбора инструмента** | 1. Открыть оба образа в двух окнах UEFITool → 2. Использовать `UEFIFind`/`UEFIExtract` для генерации отчётов → 3. Сравнить отчёты через `diff`/`Beyond Compare`. |
| **⚙️ Рекомендуемые действия** | 1. В UEFITool: `File → Export → Report` для каждого образа → получишь список файлов с GUID/смещениями.<br>2. Сравни отчёты: `diff old_report.txt new_report.txt` → найди добавленные/удалённые GUID.<br>3. Для ключевых модулей (микрокод, `NvmExpressDxe`, `SecurityPkg`): экспортируй `.efi` из обоих образов → сравни в Hезд (`Find differences`).<br>4. Проверь FIT-таблицу: `View → FIT` → сравни версии микрокода, даты. |
| **✅ Ожидаемый результат** | Список изменённых модулей, понимание, что обновили (например, `Microcode: 0xAA → 0xBB`, `NvmExpressDxe: v1.2 → v1.3`). |
| **❌ Неожиданный результат** | Отчёты идентичны, но образы разные по хешу.<br>→ **Действия**: 1) Возможны изменения в паддинге/выравнивании (не критично); 2) Проверь `RAW`-секции: возможно, изменились данные без изменения структуры; 3) Используй бинарное сравнение: `cmp -l old.bin new.bin | head -20`. |

### 🔹 Ситуация 9: «Экспортированный .efi не работает при обратной вставке»
**Симптомы**: Извлёк `bootmgfw.efi` через `Extract body`, отредактировал, вставил обратно → система не грузится.
**Причина**: При экспорте/вставке потерялись зависимости (секции `Depex`, `UI`, `Version`), или изменилось выравнивание.

| Этап | Действия |
|------|----------|
| **🎯 Алгоритм выбора инструмента** | 1. Сравнить оригинальный и модифицированный FFS-файл в Hезд → 2. Проверить наличие всех секций в UEFITool → 3. Использовать `Replace body` вместо ручного редактирования заголовка. |
| **⚙️ Рекомендуемые действия** | **Правильный воркфлоу**:<br>1. Найди файл → разверни → найди секцию `PE32 Image`.<br>2. ПКМ на `PE32 Image` → `Extract body...` → получишь чистый `.efi` (код).<br>3. Отредактируй `.efi` (патч, рекомпиляция).<br>4. Вернись к тому же файлу в UEFITool → ПКМ на `PE32 Image` → `Replace body...` → выбери новый `.efi`.<br>5. UEFITool авто-пересчитает заголовок и CRC.<br>**Если уже сломал**:<br>1. Верни оригинальный `.efi` через `Replace body`.<br>2. Если не помогло — восстанови весь файл из бэкапа. |
| **✅ Ожидаемый результат** | Модифицированный модуль встраивается без ошибок, система грузится. |
| **❌ Неожиданный результат** | Даже с оригинальным `.efi` после `Replace body` возникают ошибки.<br>→ **Действия**: 1) Возможна проблема с выравниванием: убедись, что новый `.efi` имеет размер, кратный 4/8 байтам; 2) Проверь, не изменил ли ты точку входа (`AddressOfEntryPoint`); 3) Если критично — не модифицируй загрузчик, используй внешний загрузчик (Ventoy). |

[🛡️ Общие правила безопасности при работе с UEFITool]
1. **readonly по умолчанию**: Открывай образы в режиме просмотра, включай модификацию только когда готов сохранять.
2. **Бэкап перед каждым действием**: `cp work.bin work_$(date +%s).bin` — откат за 5 секунд.
3. **Валидация — обязательный шаг**: Никогда не записывай в железо образ без `Validate → valid: true`.
4. **Не трогай неизвестное**: Если GUID unknown и нет документации — не модифицируй.
5. **Тестируй на виртуалке**: QEMU с OVMF — безопасный полигон для проверки модифицированных образов.

[RECOMMEND]
1. Создай шаблон `uefi_session.sh`/`.bat` с командами: бэкап, запуск UEFITool, валидация, логирование.
2. Потренируй Ситуацию №2 (поиск) и №6 (валидация) на тестовом образе — это основа безопасной работы.

[ANTICIPATE]
- "Как автоматически извлечь все .efi из образа?" → `UEFIExtract backup.bin report > map.json` + скрипт на `jq` для парсинга и `dd` для извлечения по смещениям.
- "Можно ли патчить образ без UEFITool?" → Да, через `hexedit` + знание структуры, но риск ошибки ×10. UEFITool берёт на себя CRC/выравнивание — это стоит использования.
